# Rule 1 - 答案必須寫進對應章節

- 每個已接受的答案必須追加到 `## 澄清紀錄 ( Clarifications )` 的當日場次，格式為 `- Q: <問題> → A: <答案>`。
- 同一個答案必須同步改寫受影響的正文，不得只留下問答紀錄。
- 功能行為必須寫入對應的功能需求。
- 角色、旅程與互動必須寫入使用者故事或驗收情境。
- 資料物件、身份或生命週期必須寫入關鍵實體。
- 品質要求必須寫入非功能需求。
- 失敗、空值與例外必須寫入邊界情境。
- 正文沒有對應章節時，必須寫入最接近的既有章節，不得另建規格裡沒有的頂層章節。

## Good Example

- 問答進入澄清紀錄，資料歸屬同時寫進關鍵實體。

```markdown
## 澄清紀錄 ( Clarifications )

### 澄清場次 ( Session ) 2026-10-13

- Q: 原始照片加入相簿後，檔案應保留在原處嗎? → A: 保留原檔，只儲存參照

## 關鍵實體 ( Key Entities )

- **照片參照**: 整理資料只儲存原始檔案的參照，不搬走原始檔案。
```

## Bad Example

- 只追加問答，關鍵實體仍寫著檔案去向尚未決定。

```markdown
- Q: 原始照片加入相簿後，檔案應保留在原處嗎? → A: 保留原檔，只儲存參照

## 關鍵實體 ( Key Entities )

- **照片**: 原始檔案的去向尚未決定。
```

# Rule 2 - 新答案必須取代矛盾內容

- 新答案使舊句子失效時，必須替換該句，不得保留互相矛盾的兩種說法。
- 新答案推翻既有假設時，必須刪除或改寫該假設。
- 同一個概念必須全篇使用同一個名稱。
- 舊稱只能保留一次，並標明原稱。
- 空泛且無法驗收的形容詞，必須改成 `成功標準 ( Success Criteria )` 裡的可量測成果。

## Good Example

- 「快速」被替換成可量測成果，舊假設一併刪除。

```markdown
## 成功標準 ( Success Criteria )

- **SC-002**: 100 張照片完成日期分組的時間不超過 3 秒。

## 假設 ( Assumptions )

- 日期分組使用照片可取得的拍攝日期。
```

## Bad Example

- 新的秒數標準已經寫入，舊的「要很快」和相反假設仍留在規格裡。

```markdown
- **SC-002**: 100 張照片完成日期分組的時間不超過 3 秒。
- **SC-003**: 整理過程要很快。

## 假設 ( Assumptions )

- 整理速度是否需要量化尚未決定。
```

# Rule 3 - 寫回必須停在需求層

- 寫回內容必須維持 Feature Specification 的需求層級。
- 使用者回答若夾帶實作方案，寫回時必須只保留會改變規格或驗收的決策。
- 不得寫入程式語言、框架、資料庫、API、雲服務、內部模組或任務拆解。
- 需要後續 planning 取捨的技術選擇，不得在這次寫回中固定。

## Good Example

- 使用者提到用腳本檢查，寫回只留下可驗收的規格約束。

```markdown
使用者回答：可以用腳本檢查，重點是原始檔案不得被搬移。

寫回功能需求：
- 整理流程必須保留原始照片檔案的位置。
```

## Bad Example

- 寫回把未確認的實作方案固定進規格。

```markdown
使用者回答：可以用腳本檢查，重點是原始檔案不得被搬移。

寫回功能需求：
- 必須新增 `scripts/check_files.py`，並在每次整理時呼叫。
```

# Rule 4 - 狀態與 checklist 必須反映寫回結果

- spec.md 仍有未回答的核心缺口，或新答案造成尚未清除的矛盾時，Status 必須維持 `Needs Clarification`。
- 核心缺口都已寫入規格，或剩餘缺口已改寫為假設時，Status 必須改為 `Ready for Planning`。
- feature 目錄已有 `checklists/requirements.md` 時，必須依寫回後的 spec.md 重新判斷每個勾選項目。
- 只有通過與否真的改變的項目可以改 `[ ]` 或 `[x]`。
- checklist 的標題、備註、順序與其他文字必須保持不變。
- 仍待使用者回答的核心缺口，其 checklist 項目不得標記為通過。

## Good Example

- 核心缺口已經寫入規格，狀態改為可進入 planning，checklist 只改動因此通過的那一項。

```markdown
**狀態 ( Status )**：Ready for Planning

- [x] 當狀態為 `Ready for Planning` 時，沒有未解決的核心澄清缺口
```

## Bad Example

- 原始檔案去向仍未回答，狀態卻已改成可進入 planning，對應 checklist 也被勾成通過。

```markdown
**狀態 ( Status )**：Ready for Planning

## 假設 ( Assumptions )

- 原始照片是否需要搬移尚未決定。

- [x] 當狀態為 `Ready for Planning` 時，沒有未解決的核心澄清缺口
```
