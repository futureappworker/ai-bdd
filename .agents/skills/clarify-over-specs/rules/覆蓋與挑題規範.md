# Rule 1 - 提問前必須先做覆蓋掃描

- 提問模式必須先完成覆蓋掃描，並在內部把每一類標成清楚、部分或缺少。
- 覆蓋結果必須只用來挑題，不得把整張覆蓋圖寫入 spec.md 或回覆。

## Good Example

- 先在內部標出資料歸屬仍缺少，再用這個結果決定要問的題，回覆裡沒有貼出整張覆蓋圖。

```markdown
內部覆蓋：領域與資料 = 缺少。選定提問：原始照片是否保留在原處。
回覆：只包含這一題的問句與選項。
```

## Bad Example

- 把領域與資料的覆蓋狀態寫進回覆，而不是只拿它來決定要問的題。

```markdown
## 覆蓋圖

- 領域與資料：缺少

## Question 1: 原始照片的去向

**What we need to know**: 原始照片加入相簿後，檔案應保留在原處嗎?
```

# Rule 2 - 只問會改變規格或驗收的事

- 進入提問的缺口必須會改變功能範圍、資料歸屬、使用者旅程、驗收結果、安全隱私要求或後續 planning 邊界。
- 實作方法、技術選型、任務拆解，以及不改變驗收的表面偏好，不得進入提問。
- 沒有會改變規格或驗收的缺口時，不得委派 `clarify`。

## Good Example

- 原始照片是否被搬移會改變資料歸屬，因此進入提問。

```markdown
選定缺口：原始照片加入相簿後，檔案是保留在原處，還是移入相簿資料夾。
```

## Bad Example

- 按鈕顏色與使用哪種資料庫都不改變這次規格的驗收，卻仍然拿來提問。

```markdown
選定缺口：主按鈕要用藍色，還是規格要改用 PostgreSQL。
```

# Rule 3 - 全程最多五題並依影響排序

- 單次提問模式最多選定五個缺口。
- 可問缺口超過五個時，必須依影響與不確定的乘積保留前五個。
- 高影響類別仍有缺口時，不得連選兩個低影響缺口而放下該高影響類別。
- 澄清紀錄已經回答的缺口不得再問。

## Good Example

- 安全隱私仍未決定，題額先留給它，而不是連問兩個不影響驗收的用詞偏好。

```markdown
1. 相簿資料是否允許上傳到外部服務?（安全隱私，高影響）
2. 原始照片被刪除時，整理項目要保留還是移除?（資料歸屬，高影響）
```

## Bad Example

- 資料是否外傳尚未決定，題額卻先用來問兩個低影響用詞。

```markdown
1. 「相簿」要不要改叫「专辑」?
2. 「照片」要不要改叫「圖片」?
```

# Rule 4 - 委派題目必須鎖定

- 委派給 `clarify` 的每一題必須包含可獨立回答的問句、對驗收或出貨的一句利害、互斥選項或五個字以內的短答約束、恰好一個推薦與理由。
- 互斥選項必須是二到五個，並保留 Custom。
- 鎖定後的題目不得在委派時改問另一個決策。
- 提問模式不得把答案寫入 spec.md。

## Good Example

- 委派內容鎖定同一個資料歸屬決策，並帶上利害、選項與推薦。

```markdown
問句：原始照片加入相簿後，檔案應保留在原處嗎?
利害：這會決定驗收時原始檔案是否仍在使用者原來的資料夾。
推薦：A — 保留原檔，只儲存參照，避免整理流程搬走使用者的檔案。
選項：A 保留原檔 / B 移入相簿資料夾 / C 複製一份 / Custom
```

## Bad Example

- 委派時只給章節標題，並在同一輪把答案寫進規格。

```markdown
委派題目：資料模型
寫入 spec.md：原始照片一律保留不變。
```
