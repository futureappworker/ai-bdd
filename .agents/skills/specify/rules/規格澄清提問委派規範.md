# Rule 1 - 待澄清規格必須委派提問

- 當本次 `spec.md` 與 `checklists/requirements.md` 都已寫入，且 `spec.md` 的狀態為 `Needs Clarification` 時，`specify` 必須委派 `clarify-over-specs` 的提問模式。
- `specify` 必須把已寫入的 Feature Specification 交給該提問模式，由 `clarify-over-specs` 委派 `clarify` 產生澄清問題。
- `specify` 不得自行寫出澄清問題。
- `specify` 不得跳過 `clarify-over-specs` 而直接委派 `clarify`。
- 使用者沒有另外提出專業需求澄清時，不得因此省略上述委派。

## Good Example

- 規格與 checklist 都已寫入且狀態是 `Needs Clarification`，因此委派提問模式，即使使用者只執行了 `specify`。

```markdown
spec.md 狀態：Needs Clarification
checklists/requirements.md：已寫入
動作：Delegate clarify-over-specs 以提問模式產生澄清問題
```

## Bad Example

- 同樣是 `Needs Clarification`，卻因為使用者沒有另外要求專業需求澄清，而在回覆中自行列出缺口。

```markdown
spec.md 狀態：Needs Clarification
checklists/requirements.md：已寫入
動作：在回覆列出缺口，不委派 clarify-over-specs
```

# Rule 2 - 可進入規劃或未寫完時不得委派提問

- 當 `spec.md` 的狀態為 `Ready for Planning` 時，`specify` 不得委派 `clarify-over-specs`。
- 當本次沒有未回答的核心缺口時，`specify` 不得委派 `clarify-over-specs`。
- 當 `spec.md` 或 `checklists/requirements.md` 因停止寫入而未寫入完成時，`specify` 不得委派 `clarify-over-specs`。

## Good Example

- 規格已可進入 planning，因此結束於規格與 checklist，不委派提問。

```markdown
spec.md 狀態：Ready for Planning
動作：不委派 clarify-over-specs
```

## Bad Example

- 規格已可進入 planning，卻仍委派提問模式。

```markdown
spec.md 狀態：Ready for Planning
動作：Delegate clarify-over-specs 以提問模式產生澄清問題
```
