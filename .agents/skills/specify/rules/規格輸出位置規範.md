# Rule 1 - 規格必須寫入 feature 專屬目錄

- Feature Specification 必須寫入 `specs/<NNN>-<feature-slug>/spec.md`。
- `<NNN>` 必須是三位數流水號。
- `<feature-slug>` 必須使用能辨識功能主題的英文小寫連字號命名。
- Spec 不得寫入 Skill 目錄、Template 目錄、README 或使用者未指定的任意位置。

## Good Example

- 路徑使用三位數流水號與可辨識的 feature slug。

```text
specs/001-photo-album-organizer/spec.md
```

## Bad Example

- 路徑缺少 feature 專屬目錄，且寫到 Template 目錄。

```text
.agents/skills/specify/templates/spec.md
```

# Rule 2 - 流水號必須依既有 specs 決定

- 建立新 Feature Specification 時，必須檢查 `specs/` 目錄中既有的 `<NNN>-<feature-slug>` 目錄。
- 新 Feature 的 `<NNN>` 必須使用目前最大流水號加一。
- 當 `specs/` 目錄不存在或沒有既有 feature 目錄時，第一個流水號必須使用 `001`。
- 若使用者明確指定既有 Feature Specification 路徑，必須使用該路徑而不是建立新流水號。

## Good Example

- 既有最大流水號是 `002`，新 feature 使用 `003`。

```text
specs/001-photo-album-organizer/spec.md
specs/002-shared-album/spec.md
specs/003-photo-export/spec.md
```

## Bad Example

- 既有最大流水號是 `002`，新 feature 卻重用 `001`。

```text
specs/001-photo-album-organizer/spec.md
specs/002-shared-album/spec.md
specs/001-photo-export/spec.md
```

# Rule 3 - Feature slug 必須來自功能主題

- Feature slug 必須由使用者需求中的主要功能主題推導。
- Feature slug 必須只包含小寫英文字母、數字與連字號。
- Feature slug 不得包含空格、底線、中文、標點符號或日期。
- Feature slug 不得使用 `feature`、`app`、`spec` 等無法辨識主題的通用名稱。

## Good Example

- Slug 能反映照片相簿整理這個主要功能。

```text
001-photo-album-organizer
```

## Bad Example

- Slug 使用通用名稱且無法辨識功能主題。

```text
001-feature
```

# Rule 4 - 寫入模式必須保護既有規格

- 當目標 `spec.md` 不存在時，`specify` 必須建立新檔案。
- 當使用者明確指定既有 Feature Specification 路徑時，`specify` 必須更新該檔案，包含狀態為 `Implemented` 的規格。
- `specify` 不得覆寫不屬於本次 Feature Specification 的檔案。

## Good Example

- 使用者指定要更新的規格即使已實作完成，仍寫回該路徑。

```text
User request: 更新 specs/001-photo-album-organizer/spec.md，加入照片遺失時的處理方式。
Status: Implemented
Target: specs/001-photo-album-organizer/spec.md
```

## Bad Example

- 使用者已指定要更新的規格，卻寫到別的 feature 目錄。

```text
User request: 更新 specs/001-photo-album-organizer/spec.md，加入照片遺失時的處理方式。
Status: Implemented
Target: specs/002-photo-export/spec.md
```

# Rule 5 - Status 必須對應輸出模式

- 初次建立且沒有核心缺口的 Spec 必須將 Status 設為 `Ready for Planning`。
- 初次建立但仍有核心缺口的 Spec 必須將 Status 設為 `Needs Clarification`。
- 僅保存中間草稿且尚未完成一致性檢查時，可以將 Status 設為 `Draft`。
- Status 不得與 Clarifications、Assumptions 或未回答核心缺口矛盾。

## Good Example

- 規格仍有未回答的核心缺口，因此狀態是 `Needs Clarification`。

```markdown
**狀態 ( Status )**：Needs Clarification

## 澄清紀錄 ( Clarifications )

### 澄清場次 ( Session ) 2026-10-06
```

## Bad Example

- 規格仍保留未回答核心缺口，卻標示為可進入 planning。

```markdown
**狀態 ( Status )**：Ready for Planning

## 假設 ( Assumptions )

- 原始照片是否需要搬移尚未決定。
```

# Rule 6 - 完成狀態只表示實作已完成

- 規格狀態 `Implemented` 只表示該 feature 的 `tasks.md` 沒有未完成任務。
- `specify` 不得將 Status 設為 `Implemented`。
- 使用者明確指定路徑並更新一份狀態為 `Implemented` 的規格時，Status 必須改依核心缺口設為 `Needs Clarification` 或 `Ready for Planning`。

## Good Example

- 使用者指定更新已實作完成的規格，因此狀態回到可進入 planning，而不是保留完成狀態。

```markdown
User request: 更新 specs/001-photo-album-organizer/spec.md，加入照片遺失時的處理方式。
**狀態 ( Status )**：Ready for Planning
```

## Bad Example

- 規格內容已重寫，狀態卻被寫成或留在實作完成。

```markdown
User request: 更新 specs/001-photo-album-organizer/spec.md，加入照片遺失時的處理方式。
**狀態 ( Status )**：Implemented
```

# Rule 7 - 未指定路徑時必須跳過已實作規格

- 使用者沒有明確指定路徑，且狀態不是 `Implemented` 的規格少於兩份時，`specify` 必須建立下一個流水號的新 feature 目錄。
- 上述選擇不得把狀態為 `Implemented` 的規格當成本次更新目標。
- 沒有狀態列的 `spec.md` 必須視為尚未完成。
- 新流水號必須仍依所有既有 feature 目錄的最大流水號加一，包含狀態為 `Implemented` 的目錄。

## Good Example

- 既有規格已實作完成且使用者未指定路徑，因此建立下一個流水號。

```text
specs/001-online-1a2b-pvp/spec.md
Status: Implemented
User request: 做一個照片匯出功能。
Target: specs/002-photo-export/spec.md
```

## Bad Example

- 使用者未指定路徑，卻把已實作完成的規格當成這次要寫的規格。

```text
specs/001-online-1a2b-pvp/spec.md
Status: Implemented
User request: 做一個照片匯出功能。
Target: specs/001-online-1a2b-pvp/spec.md
```

# Rule 8 - 多份未完成規格必須先選擇

- 使用者沒有明確指定路徑，且狀態不是 `Implemented` 的規格有兩份以上時，`specify` 必須列出這些 feature 目錄並詢問要使用哪一份。
- 使用者回答前，`specify` 不得建立新 feature 目錄，也不得寫入任何 `spec.md`。
- 沒有狀態列的 `spec.md` 必須計入尚未完成的規格。

## Good Example

- 有兩份尚未完成的規格且使用者未指定路徑，因此先詢問並停止寫入。

```text
specs/001-photo-album-organizer/spec.md
Status: Ready for Planning
specs/002-shared-album/spec.md
Status: Needs Clarification
User request: 做一個照片匯出功能。
Action: 列出 001 與 002，詢問要使用哪一份；不寫入 spec.md
```

## Bad Example

- 有兩份尚未完成的規格，卻直接建立新目錄。

```text
specs/001-photo-album-organizer/spec.md
Status: Ready for Planning
specs/002-shared-album/spec.md
Status: Needs Clarification
User request: 做一個照片匯出功能。
Target: specs/003-photo-export/spec.md
```
