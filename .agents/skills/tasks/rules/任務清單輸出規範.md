# Rule 1 - 階段來自 spec 與介面 Artifact

- 任務清單必須依序包含 Phase 1 Setup、Phase 2 Foundational、`spec.md` 的每個使用者故事一個 Phase，再接全域 NFR Phase；有驗收旅程時，總驗收 Phase 排在最後。
- 使用者故事 Phase 的標題、優先級與順序必須來自 `spec.md`，不得另從介面 `.feature` 重切故事。
- 使用者故事 Phase 內的介面情境必須來自 `features/<interface>/` 下 `.feature` 的來源對應，不得自行編造情境。
- 不屬於任何使用者故事、且對應需求編號以 `NFR-G-` 開頭的介面情境，必須依需求編號各成一個全域 NFR Phase。
- 驗收旅程來自 `features/acceptance/` 下的 `.feature`；有驗收旅程時，必須有一個標題為 `總驗收` 的 Phase。
- 沒有對應情境的使用者故事、全域 NFR 或驗收旅程時，不得建立空的 Phase。

## Good Example

- 使用者故事、全域 NFR 與總驗收各自成 Phase，來源分別是 `spec.md`、介面 `.feature` 與 acceptance feature。

```markdown
## Phase 3: User Story 1 - 以暱稱與房號進入房間（Priority: P1）

## Phase 4: User Story 2 - 房主開始對局（Priority: P2）

## Phase 5: 全域 NFR - NFR-G-001 失敗後已進入的房間仍保留

## Phase 6: 總驗收
```

## Bad Example

- 把使用者故事、全域 NFR 與驗收旅程全部混成一個跨故事 Phase。

```markdown
## Phase 3: 跨故事整包實作

- [ ] T006 bdd red：處理所有進房、開始、NFR 與驗收旅程
```

# Rule 2 - 端點小節

- 使用者故事 Phase、全域 NFR Phase 與總驗收 Phase 必須用 `###` 為該 Phase 實際有情境的介面切開端點。
- 端點小節必須包含 **Codebase**。端點小節不得列出契約檔或 **References**。
- 某個介面在該 Phase 沒有情境時，不得為它開空的端點小節。
- 端點小節的順序必須沿該 Phase 情境在來源 `.feature` 中的相對順序；同一介面的情境被另一個介面打斷時，必須分段開小節。

## Good Example

- 該故事先是後端情境，再是前端情境，所以小節順序跟著來源。

```markdown
### 後端端點：後端房間 API

**Codebase**: `backend/src/rooms/`、`backend/tests/`

### 前端端點：前端對局畫面

**Codebase**: `frontend/src/`、`frontend/tests/`
```

## Bad Example

- 該 Phase 沒有資料庫情境，仍開一個空的小節。

```markdown
### 資料庫端點：PostgreSQL 持久化介面

**Codebase**: `backend/src/db/`
```

# Rule 3 - 每個 feature 情境三個 BDD 任務

- 使用者故事 Phase、全域 NFR Phase 與總驗收 Phase 中的每個 `.feature` 情境必須依序產生委派給 `/bdd` 的 `red`、`green`、`refactor` 三個任務。
- 三個任務的 **BDD 子命令** 必須分別是 `red`、`green`、`refactor`。
- 同一情境內任務順序必須是 `red`、`green`、再 `refactor`。
- 委派 `/bdd green` 的任務必須只做該情境通過所需的最小實作。
- 委派 `/bdd refactor` 的任務必須只整理該情境綠燈觸及的測試程式；沒有可做的結構調整時，完成條件是保持行為不變並確認該情境仍通過。
- Setup 與 Foundational 沒有對應情境時，不得標 **BDD 子命令**。

## Good Example

- 同一情境拆成三個委派給 `/bdd` 的任務，而且都對應同一個場景。

```markdown
- [ ] T006 [US1] 委派 `/bdd red`：在 `backend/features/steps/房間/開房與加入.ts` 為 BE-1.1 撰寫紅燈步驟，並執行到有效失敗
  - **BDD 子命令**: red
- [ ] T007 [US1] 委派 `/bdd green`：在 `backend/src/services/room-service.ts` 只做 BE-1.1 通過所需的最小實作
  - **BDD 子命令**: green
- [ ] T008 [US1] 委派 `/bdd refactor`：只整理 BE-1.1 綠燈觸及的 step definitions、World 或 helper，並確認情境仍通過
  - **BDD 子命令**: refactor
```

## Bad Example

- 把三個子命令合成一個任務，或改回 `TDD 步驟`。

```markdown
- [ ] T006 [US1] 進房整包實作
  - **TDD 步驟**: 紅燈
```

# Rule 4 - 任務標記與描述

- 使用者故事 Phase 的每個任務必須標 [Story]，且標記對應該 Phase 的使用者故事。
- 全域 NFR Phase 與總驗收 Phase 的任務不得標 [Story]。
- 總驗收 Phase 的任務不得標 [P]。
- 每個任務的描述必須含該任務要修改的精確檔案路徑。
- 同一情境的委派 `/bdd red`、委派 `/bdd green`、委派 `/bdd refactor` 彼此串行，不得標 [P]。
- 任務要修改的檔案與同階段尚未完成的任務不同，且不依賴那些任務時，可以標 [P]。

## Good Example

- 前端初始化可平行；BDD 任務含 [US1] 與精確檔案路徑，但沒有 [P]。

```markdown
- [ ] T003 [P] 在 `frontend/package.json`、`frontend/tsconfig.json`、`frontend/index.html` 初始化前端專案
- [ ] T006 [US1] 委派 `/bdd red`：在 `backend/features/steps/房間/開房與加入.ts` 為 BE-1.1 撰寫紅燈步驟，並執行到有效失敗
```

## Bad Example

- 同一組任務裡，初始化沒有檔案路徑；BDD 任務又誤標 [P]。

```markdown
- [ ] T003 [P] 初始化前端專案
- [ ] T006 [P] bdd red：處理 BE-1.1
```

# Rule 5 - 每個任務只綁該情境的位址

- 每個任務正下方必須有 **References**。
- 一行 **References** 只能有一個位址。
- BDD 任務若指向 `features/<interface>/`，必須至少包含兩行 **References**：該情境的介面 `.feature` 位址，以及該情境使用的 `dsl.md` 句型位址。
- BDD 任務若指向 `features/acceptance/`，必須至少包含一行 **References**：該情境的 acceptance `.feature` 位址；需要輔助邊界時，可以再加契約位址。
- 契約位址在會直接改變本輪實作邊界時可以追加為第三行 **References**。
- 後端任務不得引用 DBML 或畫面。資料庫任務不得引用 OpenAPI 或畫面。前端畫面任務不得引用 OpenAPI 或 DBML。
- Setup 與 Foundational 的每一行 **References** 必須是 `plan.md` 的一個標題，或 `techstack.md` 採用技術表的一個 Area。
- 端點小節與任務清單開頭不得要求先讀完整份 `research.md`、`techstack.md`、`contracts/`、`features/acceptance/` 或整個 `features/<interface>/` 目錄。

## Good Example

- 委派給 `/bdd` 的任務必須直接指向該情境的 `.feature`；介面情境再補 `dsl.md` 句型，必要時再補契約。

```markdown
- [ ] T006 [US1] 委派 `/bdd red`：在 `backend/features/steps/房間/開房與加入.ts` 為 BE-1.1 撰寫紅燈步驟，並執行到有效失敗
  - **BDD 子命令**: red
  - **References**: `features/backend/加入房間.feature#場景:BE-1.1 玩家A、房間 2468、進入成功`
  - **References**: `features/backend/dsl.md#When:"{玩家}" 以房間代碼 "{房間代碼}" 進入房間`
  - **References**: `contracts/openapi.yaml#/paths/~1v1~1rooms~1by-code~1{code}~1join/post`
```

## Bad Example

- 只給契約，沒有 `.feature` 與 `dsl.md`。

```markdown
- [ ] T006 [US1] bdd red：處理 BE-1.1
  - **References**: `contracts/openapi.yaml#/paths/~1v1~1rooms~1by-code~1{code}~1join/post`
```

# Rule 6 - 位址寫法

- 介面情境位址必須寫成 `features/{interface}/{file}.feature#場景:{scenarioTitle}`。
- 驗收旅程位址必須寫成 `features/acceptance/{file}.feature#場景:{scenarioTitle}`。
- DSL 句型位址必須寫成 `features/{interface}/dsl.md#{Section}:{sentence}`，其中 `{Section}` 必須是 `Given`、`When` 或 `Then`。
- HTTP 操作位址必須寫成 `contracts/openapi.yaml#/paths/~1{path}/{method}`。
- `{path}` 中的每個 `/` 必須寫成 `~1`。
- 畫面位址必須寫成 `contracts/interface.pen#{frameId}`。
- DBML 位址必須寫成 `contracts/schema.dbml#Table/{name}`。
- 技術選型位址必須寫成 `techstack.md#採用技術/{Area}`。
- `plan.md` 位址必須寫成 `plan.md#{標題}`。

## Good Example

- 位址同時符合介面場景、DSL 與 OpenAPI 格式。

```markdown
  - **References**: `features/backend/加入房間.feature#場景:BE-1.1 玩家A、房間 2468、進入成功`
  - **References**: `features/backend/dsl.md#When:"{玩家}" 以房間代碼 "{房間代碼}" 進入房間`
  - **References**: `contracts/openapi.yaml#/paths/~1v1~1rooms~1by-code~1{code}~1join/post`
```

## Bad Example

- 同一組位址用了舊的 `testplan.md`，而且 DSL 沒有標出句型區段。

```markdown
  - **References**: `testplan.md#BE-1.1`
  - **References**: `features/backend/dsl.md#"{玩家}" 以房間代碼 "{房間代碼}" 進入房間`
```

# Rule 7 - 總驗收旅程也拆成三個 BDD 任務

- `features/acceptance/` 的每個驗收旅程場景必須依序產生委派給 `/bdd` 的 `red`、`green`、`refactor` 三個任務。
- 三個任務不得標 [Story]，也不得標 [P]。
- 這三個任務的 **BDD 子命令** 必須分別是 `red`、`green`、`refactor`。
- `red` 的任務描述必須含目標測試檔路徑，並寫明撰寫紅燈步驟與執行到有效失敗。
- `green` 的任務描述必須含主要實作檔路徑，並寫明只做該旅程通過所需的最小實作。
- `refactor` 的任務描述必須含測試程式或 helper 路徑，並寫明只整理該旅程綠燈觸及的測試程式，並確認情境仍通過。
- acceptance 的 BDD 任務必須至少一行 **References** 指向 acceptance feature 的場景；需要輔助邊界時，可以再加契約位址。

## Good Example

- 同一個 acceptance 場景拆成三個 BDD 子命令，而且都指向同一個旅程場景。

```markdown
- [ ] T027 委派 `/bdd red`：在 `frontend/tests/e2e/accept-match.test.ts` 為 ACC-1 撰寫紅燈步驟，並執行到有效失敗
  - **BDD 子命令**: red
  - **References**: `features/acceptance/完成一局.feature#場景:ACC-1 房主與加入者完成一局`
- [ ] T028 委派 `/bdd green`：在 `frontend/src/views/render.ts` 只做 ACC-1 通過所需的最小實作
  - **BDD 子命令**: green
  - **References**: `features/acceptance/完成一局.feature#場景:ACC-1 房主與加入者完成一局`
- [ ] T029 委派 `/bdd refactor`：只整理 ACC-1 綠燈觸及的測試程式，並確認情境仍通過
  - **BDD 子命令**: refactor
  - **References**: `features/acceptance/完成一局.feature#場景:ACC-1 房主與加入者完成一局`
```

## Bad Example

- 把 acceptance 場景保留成單一通過任務，沒有拆成 `red`、`green`、`refactor`。

```markdown
- [ ] T027 在 `frontend/tests/e2e/accept-match.test.ts` 寫入 ACC-1 並執行到通過
  - **References**: `features/acceptance/完成一局.feature#場景:ACC-1 房主與加入者完成一局`
```
