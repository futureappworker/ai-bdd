# Rule 1 - 階段來自測試計劃

- 任務清單必須依序包含 Phase 1 Setup、Phase 2 Foundational、testplan.md 的每個使用者故事章一個 Phase，再接全域 NFR Phase。有總驗收章時，總驗收 Phase 排在最後。
- 使用者故事 Phase 的數量必須等於 testplan.md 的使用者故事章數量。
- 使用者故事 Phase 的標題、優先級與案例順序必須來自該章，不得另從 spec.md 重切故事。
- 使用者故事章的每個原子案例必須留在該使用者故事 Phase，包含該章的 NFR 案例。
- 不在使用者故事章、且對應需求編號以 `NFR-G-` 開頭的原子案例，必須依需求編號各成一個全域 NFR Phase。
- 全域 NFR Phase 必須全部排在使用者故事 Phase 之後，順序必須沿用這些需求在 testplan.md 第一次出現的順序。
- 全域 NFR Phase 的標題必須以 `全域 NFR - ` 開頭，並包含該需求編號。
- 每一條全域 NFR 必須單獨成一個 Phase。不得把多條全域 NFR 合成一個 Phase，也不得把同一條全域 NFR 的案例拆到多個 Phase。
- 同一條全域 NFR 的案例順序必須沿用它所在章的 TDD 順序。
- 不在使用者故事章、不在總驗收章、且對應需求不是全域 NFR 的案例不得產生任務，也不得產生 Phase。這包含全域功能需求，以及沒有寫成總驗收案例的成功標準。
- 沒有上述全域 NFR 案例時，不得建立空的全域 NFR Phase。
- testplan.md 有總驗收章時，必須有一個標題為 `總驗收` 的 Phase。
- 總驗收 Phase 必須排在全部全域 NFR Phase 之後。沒有全域 NFR Phase 時，必須排在最後一個使用者故事 Phase 之後。
- 沒有總驗收章時，不得建立空的總驗收 Phase。
- 任務清單不得包含名為跨故事的 Phase。
- 骨架與範例中的故事、任務編號與端點名稱是已確認範例的填法。產出時必須改成這次 testplan.md 的故事與案例，不得照抄範例任務。

## Good Example

- 兩則使用者故事之後，NFR-G-001 與 NFR-G-003 各佔一個 Phase，最後是總驗收。全域功能需求沒有任務。

```markdown
## Phase 3: User Story 1 - 以暱稱與房號進入房間（Priority: P1）

## Phase 4: User Story 2 - 房主開始對局（Priority: P2）

## Phase 5: 全域 NFR - NFR-G-001 失敗後已進入的房間仍保留

## Phase 6: 全域 NFR - NFR-G-003 房間讀取在 1 秒內回傳

## Phase 7: 總驗收
```

## Bad Example

- 同一組 NFR-G-001、NFR-G-003 與 ACC-1 被合成一個名為跨故事的 Phase，並把全域功能需求 FR-G-004 也寫成任務。

```markdown
## Phase 3: User Story 1 - 以暱稱與房號進入房間（Priority: P1）

## Phase 4: User Story 2 - 房主開始對局（Priority: P2）

## Phase 5: 跨故事 - 房間資料可再讀

- [ ] T021 紅燈：寫入 NFR-G-001
- [ ] T024 紅燈：寫入 NFR-G-003
- [ ] T027 紅燈：寫入 ACC-1
- [ ] T030 紅燈：寫入 FR-G-004
```

# Rule 2 - 端點小節

- 使用者故事 Phase、全域 NFR Phase 與總驗收 Phase 必須用 `###` 為該 Phase 實際有案例的介面切開端點。
- 端點小節必須包含 **Codebase**。端點小節不得列出契約檔或 **References**。
- 某個介面在該 Phase 沒有案例時，不得為它開空的端點小節。
- 端點小節的順序必須沿該 Phase 案例在所屬章 TDD 順序中的相對順序；同一介面的案例被另一個介面打斷時，必須分段開小節，不得把同一介面的任務集中到順序之外。

## Good Example

- 進房章先是後端案例，接著才是前端案例，所以前端小節排在後端小節之後。

```markdown
### 後端端點：後端房間 API

**Codebase**: `backend/src/rooms/`、`backend/tests/`

### 前端端點：前端對局畫面

**Codebase**: `frontend/src/`、`frontend/tests/`
```

## Bad Example

- 該 Phase 沒有資料庫案例，仍開一個空的資料庫端點。

```markdown
### 資料庫端點：PostgreSQL 持久化介面

**Codebase**: `backend/src/db/`
```

# Rule 3 - 每個案例三個 TDD 任務

- 使用者故事 Phase 與全域 NFR Phase 中的每個原子案例必須依序產生紅燈、綠燈、重構三個任務。
- 三個任務的 **TDD 步驟** 必須分別是 `紅燈`、`綠燈`、`重構`。
- 任務在所屬 Phase 的順序必須等於這些案例在所屬章 TDD 順序中的相對順序；同一案例內必須是紅燈、綠燈、再重構。
- 綠燈任務必須只做該案例通過所需的最小實作。
- 重構任務必須只整理該案例綠燈觸及的實作；沒有可做的結構調整時，完成條件是保持行為不變並確認該案例測試仍通過。
- 不列為案例不得產生任務。
- Setup 與 Foundational 沒有對應案例時，不得標 **TDD 步驟**。

## Good Example

- BE-1.1 依序是紅燈、綠燈、重構，而且都指向同一個案例。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **TDD 步驟**: 紅燈
- [ ] T007 [US1] 綠燈：在 `backend/src/rooms/enter.ts` 做 BE-1.1 通過所需的最小實作
  - **TDD 步驟**: 綠燈
- [ ] T008 [US1] 重構：只整理 BE-1.1 綠燈觸及的實作；沒有可做的結構調整時保持行為不變，並確認測試仍通過
  - **TDD 步驟**: 重構
```

## Bad Example

- 同一個案例把紅燈和綠燈合成一個任務，並把重構留到全部故事結束之後。

```markdown
- [ ] T006 [US1] 撰寫 BE-1.1 測試並實作進入房間
- [ ] T099 重構全部使用者故事
```

# Rule 4 - 任務標記與描述

- 使用者故事 Phase 的每個任務必須標 [Story]，且標記對應該 Phase 的使用者故事。
- 全域 NFR Phase 與總驗收 Phase 的任務不得標 [Story]。
- 總驗收 Phase 的任務不得標 [P]，也不得標 **TDD 步驟**。
- 每個任務的描述必須含該任務要修改的精確檔案路徑。
- 同一章的紅燈、綠燈、重構不得標 [P]。
- 任務要修改的檔案與同階段尚未完成的任務不同，且不依賴那些任務時，可以標 [P]。
- 任務要修改的檔案與同階段尚未完成的任務相同，或依賴那些任務時，不得標 [P]。

## Good Example

- 前端初始化與同階段的後端初始化修改不同檔案，所以可以標 [P]。進房紅燈標了 [US1]，描述含測試檔路徑，而且沒有標 [P]。

```markdown
- [ ] T003 [P] 在 `frontend/package.json`、`frontend/tsconfig.json`、`frontend/index.html` 初始化前端專案
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
```

## Bad Example

- 同一組任務裡，前端初始化沒有檔案路徑。進房紅燈標了 [P]，沒有 [US1]，描述也沒有測試檔路徑。

```markdown
- [ ] T003 [P] 初始化前端專案
- [ ] T006 [P] 紅燈：寫入 BE-1.1，並執行到預期失敗
```

# Rule 5 - 每個任務只綁該案例的位址

- 每個任務正下方必須有 **References**。
- 一行 **References** 只能有一個位址。
- TDD 任務必須正好兩行 **References**：`testplan.md#{案例 ID}`，以及該案例契約位址的同一條位址。
- 後端任務不得引用 DBML 或畫面。資料庫任務不得引用 OpenAPI 或畫面。前端畫面任務不得引用 OpenAPI 或 DBML。
- Setup 與 Foundational 的每一行 **References** 必須是 `plan.md` 的一個標題，或 `techstack.md` 採用技術表的一個 Area。
- 端點小節與任務清單開頭不得要求先讀完整份 research.md、techstack.md、contracts/ 或 testplan.md。

## Good Example

- 進房紅燈同時指向測試計劃案例與該案例的進入操作。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **TDD 步驟**: 紅燈
  - **References**: `testplan.md#BE-1.1`
  - **References**: `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
```

## Bad Example

- 前端任務改指 OpenAPI，而且沒有測試計劃案例位址。

```markdown
- [ ] T012 [US1] 紅燈：寫入 FE-1.1
  - **References**: `contracts/openapi.yaml`
```

# Rule 6 - 位址寫法

- 案例位址必須寫成 `testplan.md#{案例 ID}`。
- HTTP 操作位址必須寫成 `contracts/openapi.yaml#/paths/~1{path}/{method}`。
- `{path}` 中的每個 `/` 必須寫成 `~1`。
- `#/paths/` 與 method 前的 `/` 必須保留。
- 畫面位址必須寫成 `contracts/interface.pen#{frameId}`。
- DBML 位址必須寫成 `contracts/schema.dbml#Table/{name}`。
- 技術選型位址必須寫成 `techstack.md#採用技術/{Area}`，`{Area}` 必須是採用技術表的一個 Area。
- `plan.md` 位址必須寫成 `plan.md#{標題}`，`{標題}` 必須是 `plan.md` 的一個標題。

## Good Example

- 進入操作的路徑斜線寫成 `~1`。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **References**: `testplan.md#BE-1.1`
  - **References**: `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
```

## Bad Example

- 同一條進入操作裡，`rooms` 與 `enter` 前面的斜線沒有寫成 `~1`。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **References**: `testplan.md#BE-1.1`
  - **References**: `contracts/openapi.yaml#/paths/~1api/rooms/enter/post`
```

# Rule 7 - 總驗收案例只產生一個通過任務

- 總驗收章的每個原子案例必須產生一個任務。
- 該任務不得標 **TDD 步驟**，不得標 [Story]，不得標 [P]。
- 任務描述必須含測試檔路徑，並寫明執行到通過。
- 失敗時可修正的實作檔必須寫在同一條任務描述。
- 該任務不得拆成紅燈、綠燈、重構。
- 該任務必須正好兩行 **References**：`testplan.md#{案例 ID}`，以及該案例契約位址的同一條位址。
- 多個總驗收案例時，任務順序必須沿用總驗收章的 TDD 順序。

## Good Example

- ACC-1 只有一個任務，寫入測試並執行到通過。

```markdown
- [ ] T027 在 `frontend/tests/e2e/accept-match.test.ts` 寫入 ACC-1 並執行到通過；失敗時只修正 `frontend/src/screens/match.ts` 使這條旅程通過
  - **References**: `testplan.md#ACC-1`
  - **References**: `contracts/interface.pen#in-match`
```

## Bad Example

- 同一個 ACC-1 被拆成紅燈、綠燈、重構。

```markdown
- [ ] T027 紅燈：在 `frontend/tests/e2e/accept-match.test.ts` 寫入 ACC-1，並執行到預期失敗
  - **TDD 步驟**: 紅燈
- [ ] T028 綠燈：在 `frontend/src/screens/match.ts` 做 ACC-1 通過所需的最小實作
  - **TDD 步驟**: 綠燈
- [ ] T029 重構：整理 ACC-1
  - **TDD 步驟**: 重構
```
