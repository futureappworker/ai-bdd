# Rule 1 - 回覆前必須求出下一個未完成任務 ID

- 進入回覆 Phase 前，必須依 `tasks.md` 文件順序求出第一個仍為 `[ ]` 的任務 ID；若不存在，該值必須為空。
- 當第一個未完成任務 ID 存在時，必須把它當成是否允許結束的主要判定輸入。
- 不得只用「本輪已完成很多任務」或「已跨到下一個故事」取代第一個未完成任務 ID 的判定。

## Good Example

- 先求出 `T069`，再依是否有硬阻擋決定回到下一個任務或結束。

```markdown
tasks.md：
- [X] T068 …
- [ ] T069 …

第一個未完成任務 ID：T069
下一步：檢查是否有硬阻擋；若無，回到 Phase 3
```

## Bad Example

- 沒有先求出第一個未完成任務 ID，就直接用進度摘要收尾。

```markdown
tasks.md：
- [X] T068 …
- [ ] T069 …

回覆：本輪先完成 T051-T068
```

# Rule 2 - 有下一個未完成任務且無硬阻擋時不得回覆收尾

- 第一個未完成任務 ID 存在且未命中硬阻擋時，下一個執行位置必須是 Phase 3。
- 上述情況下不得產生任何使用者可見的收尾回覆、進度摘要、checkpoint 報告或「先做到這裡」式訊息。
- 上述情況下不得以回合長度、故事切換、已完成批次很多、或想整理摘要為由進入 Phase 13。

## Good Example

- `T069` 仍未完成且工具可用，因此不回覆，直接回到下一個任務。

```markdown
第一個未完成任務 ID：T069
硬阻擋：無
下一個執行位置：Phase 3
使用者可見回覆：無
```

## Bad Example

- `T069` 仍未完成且沒有硬阻擋，卻先發出本輪完成摘要。

```markdown
第一個未完成任務 ID：T069
硬阻擋：無
下一個執行位置：Phase 13
回覆：本輪完成 T051-T068，下一個 T069
```

# Rule 3 - 因硬阻擋或環境上限結束時必須帶出阻擋證據

- 第一個未完成任務 ID 存在且要進入 Phase 13 時，回覆必須明確寫出硬阻擋或環境上限原因。
- 第一個未完成任務 ID 存在且要進入 Phase 13 時，回覆必須明確寫出 `implement 未跑完` 與該任務 ID。
- 不得在沒有阻擋證據時，把「下一個任務 ID」包裝成一般進度提示或建議下次再跑。

## Good Example

- 因驗證修正後仍失敗而停止，回覆同時帶出阻擋原因與下一個任務 ID。

```markdown
implement 未跑完
阻擋原因：T069 依任務驗證規範完成修正後仍無法通過
下一個未完成任務 ID：T069
```

## Bad Example

- 沒有阻擋證據，卻把未完成任務留到下一輪。

```markdown
本輪先做到這裡
下一個未完成任務 ID：T069
```
