# Rule 1 - 判定硬阻擋前必須保留最新失敗證據

- 本次目標任務要以硬阻擋停止前，必須先保留該任務最新一次驗證或情境命令的失敗證據。
- 失敗證據必須至少包含：當前任務 ID、最新命令或情境位址、最新失敗摘要。
- 不得只用「看起來很難修」或「先做到這裡」當作硬阻擋證據。

## Good Example

- 先保留最新失敗，再判定是否需要停止。

```text
任務：T087
最新命令：npx playwright test --grep "FE-7.2"
最新失敗：chat-messages 在 10 秒內仍看不到「還在嗎」
```

## Bad Example

- 沒有最新失敗證據就直接說卡住。

```text
任務：T087
回覆：這裡有點卡，先停
```

# Rule 2 - 還有下一個具體嘗試時不得判定硬阻擋

- 若本次目標任務仍存在一個位於任務目標檔、相鄰測試檔或 `References` 範圍內的下一個具體嘗試，處置必須是繼續本任務，不得判定硬阻擋。
- 下一個具體嘗試必須能明確指出要修改或驗證的檔案、命令或檢查點。
- 不得因為已經試過數次、已花較久時間、或已完成許多其他任務，就把仍可具體嘗試的任務改判成硬阻擋。

## Good Example

- 還能指出下一個 task-local 修正，因此繼續本任務。

```text
任務：T087
最新失敗：重連後 chat-messages 沒更新
下一個具體嘗試：在 frontend/src/main.ts 重連後立即 refreshChat()
處置：繼續 T087
```

## Bad Example

- 明明還說得出下一個 task-local 修正，卻直接停止。

```text
任務：T087
最新失敗：重連後 chat-messages 沒更新
下一個具體嘗試：調整 frontend/src/main.ts 的 refreshChat
處置：硬阻擋，先停
```

# Rule 3 - 硬阻擋只限於已無 task-local 下一步或需要外部決策

- 本次目標任務只有在下列情況才可以判定為硬阻擋：
  - 依規範完成 task-local 修正後，已無下一個具體嘗試；
  - `References` 互相矛盾或契約與情境衝突，且需要使用者決策；
  - 本任務需要的工具、命令或獨立委派模式在目前環境不可用。
- 當阻擋來自 BDD 任務時，必須先排除同一子命令下仍可繼續的修正或重跑。
- 不得把「想先總結」、「已跨故事」、「已做很多項」視為硬阻擋。

## Good Example

- 已排除 task-local 下一步，且衝突確實需要使用者決策。

```text
任務：T120
最新失敗：openapi.yaml 要求 403，但 feature 明確要求 200
task-local 下一步：無
阻擋類型：契約與情境矛盾，需使用者決策
```

## Bad Example

- 只是做了一輪修補就主觀認定卡住。

```text
任務：T087
最新失敗：chat-messages 沒更新
阻擋類型：大概很難修
```

# Rule 4 - 以硬阻擋停止時回覆必須可追溯

- 因硬阻擋停止時，回覆必須標明 **implement 未跑完**、當前任務 ID、最新失敗摘要與阻擋原因。
- 因硬阻擋停止時，回覆必須說明為什麼已無 task-local 下一個具體嘗試，或為什麼需要使用者決策。
- 不得只留下任務 ID 而省略阻擋依據。

## Good Example

- 回覆能追溯到任務、失敗與停止原因。

```text
implement 未跑完
當前任務：T087
最新失敗：FE-7.2 重連後 10 秒內仍看不到「還在嗎」
阻擋原因：已排除 step、fixture 與等待條件，下一步需要改動未列於本任務目標檔的同步策略，需重新決定邊界
```

## Bad Example

- 只有停止結論，沒有阻擋依據。

```text
implement 未跑完
下一個任務：T087
```
