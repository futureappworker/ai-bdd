# Rule 1 - 變更範圍必須只滿足目標任務

- 原始碼、測試或文件變更必須直接服務於目標任務的描述與 `References`。
- 可以建立目標任務需要的最小輔助型別、函式或檔案。
- 不得實作本次目標任務以外的未完成任務所描述的行為。
- 不得把 unrelated refactor、格式化全專案或依賴升級混入目標任務。

## Good Example

- 目標任務只處理單一聊天室情境，不提前做下一個拒絕規則。

```markdown
目標任務：T005 在 backend/src/rooms/chat-service.ts 完成 BE-1.1 的最小實作
本次變更：送出成功與訊息落庫
未做：超字數拒絕、離房清空
```

## Bad Example

- 順手實作尚未選擇的其他情境。

```markdown
目標任務：T005 在 backend/src/rooms/chat-service.ts 完成 BE-1.1 的最小實作
本次變更：送出成功、超字數拒絕、離房清空
```

# Rule 2 - 非 BDD 測試任務必須先看到有效失敗

- 目標任務是未標 **BDD 子命令** 的測試任務時，必須先寫入該測試任務要求的斷言。
- 新測試必須在對應實作完成前執行並取得有效失敗結果。
- 測試失敗原因必須對應尚未實作的目標行為，不得是語法錯誤、錯誤 import 或測試環境缺失。
- 若新測試無法執行到有效失敗，必須修正測試任務本身，不得將任務打勾。

## Good Example

- 測試失敗原因是聊天室尚未留下訊息。

```text
FAIL chat-message.feature
Expected latest message to equal "哈囉"
Received []
```

## Bad Example

- 測試失敗原因是 step 檔載入錯誤，不能視為有效失敗。

```text
FAIL chat-message.feature
Cannot find module "../steps/聊天送出"
```

## Exceptions

- 任務標有 **BDD 子命令** 時，`implement` 必須依 `BDD子命令委派規範` 委派給 `/bdd`，並以 `/bdd` 的結果決定是否打勾或停止。
- `References` 指向 `features/acceptance/` 且標有 **BDD 子命令** 的任務不適用本規則；該類任務應依 Rule 4 委派給 `/bdd`，而不是要求單一直接通過。
- 由 `tasks` 主流程產出的介面情境測試任務應由 `/bdd` 承接；只有 `tasks.md` 明確存在未標 **BDD 子命令** 的測試任務時，才適用本規則。

# Rule 3 - 實作任務必須優先滿足既有測試與契約

- 目標任務是實作任務時，必須先找出對應場景、DSL 句型或最小契約驗證方式。
- 實作必須滿足已選任務列出的權威位址與錯誤路徑。
- 不得修改測試來配合錯誤實作，除非測試本身與權威位址矛盾。
- 若測試與權威位址矛盾，必須回報矛盾，並只修正與權威位址矛盾的測試，不得因此結束後續任務。

## Good Example

- 實作依場景與 DSL 句型讓聊天對話保留送出的訊息。

```typescript
return { ok: true, seq };
```

## Bad Example

- 實作回傳未在權威位址中的欄位，並改測試接受它。

```typescript
return { accepted: true, messageSeq: seq };
```

## Exceptions

- 任務標有 **BDD 子命令** 時，`implement` 必須依 `BDD子命令委派規範` 委派給 `/bdd`，並以 `/bdd` 的結果決定是否打勾或停止。

# Rule 4 - acceptance BDD 任務必須沿用驗收旅程權威

- 任務 `References` 指向 `features/acceptance/` 且標有 **BDD 子命令** 時，該任務是 acceptance BDD 任務。
- `red` 必須以該 acceptance 場景的旅程終點或中途觀察作為有效失敗證據，不得以測試環境錯誤充當紅燈。
- `green` 必須只做該 acceptance 場景通過所需的最小實作，不得提前實作下一個未完成旅程。
- `refactor` 必須只整理該 acceptance 場景綠燈觸及的測試程式，並確認該場景仍通過。
- acceptance BDD 任務可以委派給 `/bdd`，不得改回單一「直接通過」任務。

## Good Example

- 同一個 acceptance 場景拆成 `red`、`green`、`refactor`，並只推進當前子命令。

```text
任務：T018 委派 /bdd red 處理 ACC-1
References：features/acceptance/完成一局.feature#場景:ACC-1 房主與加入者完成一局
結果：FAIL journey endpoint not reached
完成：是，視為有效紅燈
```

## Bad Example

- 把 acceptance 場景留成單一直接通過任務，沒有拆成 BDD 子命令。

```text
任務：T018 在 frontend/tests/e2e/chat-journey.test.ts 寫入 acceptance 場景並執行到通過
結果：PASS
完成：是
```

# Rule 5 - 驗證與探索必須鎖定當前任務邊界

- 選定本次目標任務後，讀取、測試、驗證與探索行為必須只圍繞該任務描述、目標檔案與 `References` 指向的場景、DSL、契約或驗收旅程。
- 不得主動執行其他未完成任務的場景、其他未完成任務的測試命令，或與本次目標任務無關的探索命令。
- 範圍外場景或測試結果不得作為本次目標任務的打勾依據、停止依據、回覆摘要依據或「先做到這裡」的理由。
- 發現範圍外場景失敗時，若本次目標任務仍可依既有 `References` 繼續執行，必須忽略該結果並回到本次目標任務。
- 只有當本次目標任務自己的 `References` 無效、彼此矛盾，或依既有規範修正後仍無法通過時，才可以把該任務視為硬阻擋。

## Good Example

- 本次目標任務是 `T051`，因此只執行 `FE-R1` 所需場景，沒有先去跑 `FE-1.4`。

```text
本次目標任務：T051
References：features/frontend/讀取聊天對話.feature#場景:FE-R1 玩家B、房間 3601、剛加入
本次命令：npx playwright test --grep "FE-R1 玩家B、房間 3601、剛加入"
處置：依 FE-R1 結果決定打勾或停止
未做：FE-1.4、FE-5、FE-8.2
```

## Bad Example

- 本次目標任務是 `T051`，卻先跑 `FE-1.4`，再用其失敗當成停下理由。

```text
本次目標任務：T051
本次命令：npx playwright test --grep "FE-1.4 玩家B、房間 3404、訊息1234"
回覆：FE-1.4 尚未完成，所以本輪先停在這裡
```
