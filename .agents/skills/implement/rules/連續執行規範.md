# Rule 1 - 任務已打勾就回到下一個任務

- 本次目標任務的 checkbox 為 `[X]` 時，下一個執行位置必須是 Phase 3。
- 任務之間不得詢問使用者是否繼續。
- `STOP and VALIDATE`、`MVP First`、`MVP 止於`、`Parallel Opportunities` 與使用者指定的任務 ID 不得作為進入 Phase 13 的條件。

## Good Example

- T002 已打勾，後面還有 T003，因此回到選擇下一個任務。

```markdown
- [X] T002 初始化 backend 專案
- [ ] T003 初始化 frontend 專案

本次目標任務：T002
下一個執行位置：Phase 3
```

## Bad Example

- T002 已打勾且 T003 尚未完成，卻結束本次執行。

```markdown
- [X] T002 初始化 backend 專案
- [ ] T003 初始化 frontend 專案

本次目標任務：T002
下一個執行位置：Phase 13
```

# Rule 2 - 任務未能打勾就結束本次執行

- 本次目標任務的 checkbox 仍是 `[ ]` 時，下一個執行位置必須是 Phase 13。
- checkbox 仍是 `[ ]` 只發生在憲法停止寫入 `tasks.md`。
- 結束回覆不得詢問使用者是否繼續。

## Good Example

- 憲法停止寫入 checkbox，T002 維持未完成，因此結束本次執行。

```markdown
憲法 Rule：停止寫入 tasks.md
- [ ] T002 初始化 backend 專案

本次目標任務：T002
下一個執行位置：Phase 13
```

## Bad Example

- 憲法已停止寫入 checkbox，卻回去做下一個任務。

```markdown
憲法 Rule：停止寫入 tasks.md
- [ ] T002 初始化 backend 專案

本次目標任務：T002
下一個執行位置：Phase 3
```

# Rule 3 - Phase 13 只在允許結束時進入

- `tasks.md` 仍有 checkbox 為 `[ ]` 的任務，且本次目標任務已成功打勾為 `[X]` 時，下一個執行位置必須是 Phase 3，不得進入 Phase 13。
- 進入 Phase 13 的允許情況只有：`tasks.md` 已無未完成任務且已走完 Phase 9 到 Phase 12，或憲法停止寫入 `tasks.md` 導致本次目標任務無法打勾，或已命中 Rule 4 定義的硬阻擋或環境上限。
- 同一輪 `/implement` 必須在允許範圍內盡可能連續執行 Phase 3 到 Phase 12，直到無未完成任務或命中上述硬阻擋。
- 回覆不得把「再呼叫 /implement」「再執行一次 /implement」當成正常結束後的建議下一步；不得在尚有未完成任務時，用進度摘要或 checkpoint 名稱暗示可以收工。
- 若因回合或環境限制無法在同一回覆內繼續下一個任務，仍須在回覆中標明 **implement 未跑完**，並寫出文件順序上的下一個未完成任務 ID；不得偽裝成已依 SOP 正常結束。

## Good Example

- 全部任務已 `[X]`，走完狀態更新與結束檢查後再回報完成。

```markdown
- [X] T069 …
- [X] T070 …

本次：無未完成任務
下一個執行位置：Phase 9 → Phase 12 → Phase 13
回覆：全部 70 項任務已完成
```

## Bad Example

- T010 仍是 `[ ]`，卻結束並建議使用者再叫 /implement。

```markdown
- [X] T009 …
- [ ] T010 …

回覆：已完成 T001-T009。再執行 /implement 會從 T010 繼續。
```

# Rule 4 - 能繼續就必須繼續做到完成

- 預設目標是 **同一輪使用者訊息內** 盡量跑完 `tasks.md` 全部任務，而不是每做幾項就結束回覆。
- 本次目標任務已打勾、仍有未完成任務、且 **未命中硬阻擋** 時，必須在同一輪內回到 Phase 3，不得進入 Phase 13，不得先寫給使用者的進度摘要、checkpoint 報告或「本輪完成 Txxx-Tyyy」式收工。
- **硬阻擋** 只包含：
  - Phase 2：規格品質 checklist 未完成且使用者未允許略過；
  - Phase 8：憲法停止寫入 `tasks.md`，導致無法打勾；
  - Phase 6 到 Phase 7：本次目標任務驗證在依規範修正後仍無法通過，且已依 [任務驗證規範](任務驗證規範.md) 完成修正嘗試；
  - Phase 4 到 Phase 5：任務 References 無效、契約與測試矛盾且無法在不違規格下修正，需使用者決策；
  - 使用者明確要求停止或縮小範圍。
- **不得**因下列理由提前進入 Phase 13：任務很多、已跨使用者故事、已達 MVP、想整理摘要、token 或篇幅「看起來夠長」、或慣性結束回合。
- **環境上限**：若已無法再執行下一任務所需的工具，例如無法再跑測試或寫檔，才可因環境上限進入 Phase 13；回覆必須標 **implement 未跑完**、簡述阻礙，並寫出下一個未完成任務 ID。在工具仍可用的情況下，不得以此為由收工。
- tasks 全部 `[X]` 後，依 Phase 9 到 Phase 12 更新並檢查 `spec.md`，再 Phase 13 回報 **全部完成**。

## Good Example

- T039 打勾後 T040 仍 `[ ]`，無硬阻擋，同一輪繼續 T040，不先回覆使用者。

```markdown
本次目標任務：T039 [X]
tasks.md：仍有 T040…
硬阻擋：無
下一個執行位置：Phase 3（同一輪繼續，無使用者可見回覆）
```

## Bad Example

- T039 打勾後以「implement 未跑完、下一個 T040」收工，但尚未嘗試 T040 且工具仍可用。

```markdown
本次目標任務：T039 [X]
回覆：本輪完成 T010-T039，未跑完，下一個 T040
（未執行 T040 即 Phase 13）
```

# Rule 5 - 回覆前必須再次檢查是否允許結束

- 進入回覆 Phase 前，必須再次讀取 `tasks.md` 並確認目前是否仍有未完成任務。
- `tasks.md` 仍有 `[ ]` 且未命中硬阻擋時，下一個執行位置必須是 Phase 3，不得直接產生回覆。
- `tasks.md` 已無未完成任務時，必須先完成 `spec.md` 狀態更新與檢查，再進入 Phase 13。
- 因硬阻擋或環境上限進入 Phase 13 時，回覆必須包含 **implement 未跑完**、阻擋原因與下一個未完成任務 ID。

## Good Example

- Phase 12 重讀後發現 T041 仍未完成且工具可用，因此返回下一個任務。

```markdown
Phase 12 檢查：
- [X] T040 …
- [ ] T041 …
硬阻擋：無
下一個執行位置：Phase 3
```

## Bad Example

- Phase 12 已看到 T041 仍未完成，卻仍直接進入回覆。

```markdown
Phase 12 檢查：
- [X] T040 …
- [ ] T041 …
回覆：本輪先做到這裡
```

# Rule 6 - 完成一批任務後不得直接以批次摘要收尾

- 同一輪若已連續完成多個任務，必須仍以文件順序上的第一個未完成任務 ID 判定是否繼續，不得因批次成果明顯就進入 Phase 13。
- 「本輪完成 T051-T068」「已完成 US1，下一步 US2」或同型句子，若第一個未完成任務 ID 仍存在且未命中硬阻擋，必須視為違規收尾。
- 只有在已命中硬阻擋或環境上限時，才可以在回覆中總結一批已完成任務；此時必須同時標明 **implement 未跑完**、阻擋原因與第一個未完成任務 ID。

## Good Example

- 即使剛完成一整批 US1 任務，只要 `T069` 仍未完成且工具可用，就繼續執行而不回覆。

```markdown
本輪剛完成：T051-T068
第一個未完成任務 ID：T069
硬阻擋：無
下一個執行位置：Phase 3
使用者可見回覆：無
```

## Bad Example

- 剛完成一整批 US1 任務，就直接用批次摘要收尾，沒有先處理 `T069`。

```markdown
本輪剛完成：T051-T068
第一個未完成任務 ID：T069
硬阻擋：無
回覆：本輪完成 T051-T068，下一個 T069
```
