# Rule 1 - 介面層不得沿用 acceptance 的流程粒度

- `features/acceptance/` 的旅程場景可以（且通常）在單一場景用多個 `而且` 串接流程，以驗證跨階段結果。
- `features/<interface>/` 的 `.feature` **不得**把 acceptance 長旅程原封不動搬下來當介面場景。
- 介面層的每一條場景必須像單元／整合測試：**一次只演練一個被測動作**。
- 流程款粒度的驗收留在 acceptance；介面款粒度的驗證留在 backend／frontend。

## Good Example

- acceptance 一條 SBE 旅程；介面拆成多個 Rule、多個場景，各只有一個 `當`。

```text
acceptance: SBE-1 開局前聊到加入者猜中（多個而且、一個當區塊串整段）
backend:    BE-1.1 大廳房主送等你；BE-1.2 加入者回來了；… 各一個當
```

## Bad Example

- 介面檔案只有一個場景，把 SBE-1 從進房到終局全部塞在單一 `當` 的 `而且` 鏈裡。

```gherkin
    場景: BE-1 開局前聊到加入者猜中
      當 以下玩家送出房間代碼
      而且 "玩家A" 對房間送出訊息 "等你"
      而且 …（十餘個而且）
```

# Rule 2 - 一條 Rule 只證明一個可獨立陳述的主張

- 介面 `Rule` 名稱必須寫成**一個**「必須」型主張，切到不能再切而不混淆驗證目標為止。
- 同一 acceptance `Rule` 若涵蓋多個主張（送出、讀取、拒絕、不改對局），必須拆成多條介面 `Rule`。
- 不得為了減少 Rule 數量，把「連續送出」與「終局不改勝者」寫在同一 Rule 底下混測。
- 細粒度標竿：`gherkin-and-dsl/examples/features/backend/` 的電商範例（如 `加入購物車.feature`、`付款.feature`）。

## Good Example

```gherkin
  Rule: 房間只有一人時必須拒絕送出且不留下訊息
  Rule: 沒有可送出的內容時必須拒絕且不留下訊息
```

## Bad Example

```gherkin
  Rule: 房間只有一人或沒有內容時必須拒絕送出且不留下訊息
    場景: …只有一人…
    場景: …只有空白…
```

# Rule 3 - 每個場景必須符合 3A 且只有一個當

- **Arrange**：允許多句 `假設` 與 `而且`（含高階假設、Data Table）。
- **Act**：整個場景**只能有一個** `當`；不得再寫第二個 `當`，也不得在 `當` 後用 `而且` 接第二個被測動作。
- **Assert**：允許多句 `那麼` 與 `而且`，觀察與被測動作直接相關的欄位。
- 被測動作對後端即**只打一次**目標 API（或唯一一次讀取／離開等介面操作）；對前端即**只做一次**使用者操作入口。
- 必須遵守 [Gherkin步驟格式規範](../gherkin-and-dsl/rules/Gherkin步驟格式規範.md) Rule 2。

## Good Example

```gherkin
    場景: BE-1.2 玩家A、玩家B、房間 2468、訊息來了
      假設 雙方已在大廳房間代碼 "2468"
      而且 房間 "2468" 已有聊天訊息
        | 順序 | 發送者 | 內容 |
        | 1    | 房主   | 等你 |
      當 "玩家B" 對房間送出訊息 "來了"
      那麼 房間 "2468" 的聊天對話應該符合
        | 順序 | 發送者 | 內容 |
        | 1    | 房主   | 等你 |
        | 2    | 加入者 | 來了 |
```

## Bad Example

- 同一場景兩個被測動作：`當` 後接 `而且` 第二次送出。

```gherkin
      當 "玩家B" 對房間送出訊息 "第一"
      而且 "玩家B" 對房間送出訊息 "第二"
```

- 應拆成兩個 Rule／場景，或第二次改為唯一 `當`、第一次改入 `Given`（見 Rule 4）。

# Rule 4 - 旅程前置必須收成高階 Given 與可複用 dsl.md 句型

- acceptance 裡出現在 `當` 之前、又會在多條介面場景重複的步驟，必須優先收成介面 `Given` 句型（寫入該介面 `dsl.md`）。
- 允許的高階假設包括：兩人已在大廳、房間已有聊天訊息、對局在某階段、某玩家已斷線、同房代碼換人等；語意不得超出 acceptance 與 `spec.md`。
- 同一 package 內較早介面場景建立的狀態，若後續場景需要，必須用**同名** `Given` 重現，不得假設前一個場景已執行。
- 新增高階 `Given` 時，必須在同輪一併更新 `.feature` 與 `dsl.md`。
- 已確認範例：`specs/002-player-chat/features/<interface>/dsl.md` 與對應 `.feature`。

## Good Example

- SBE-4 連續兩則：第一則為唯一 `當`；第二則 `Given 房間已有聊天訊息` 後再一次 `當`。

## Bad Example

- 為省 Given，在單一場景用兩次 `當` 或 `當`+`而且` 連續送出以模擬「連續」。

# Rule 5 - 檔案與場景編號依介面動作與面向拆分

- 介面 `.feature` 檔名必須點出**介面動作或觀察面向**（如 `送出聊天訊息`、`拒絕聊天送出`、`讀取聊天對話`），不得以 acceptance 旅程名稱當檔名（如 `聊天與對局`）。
- 同一檔案可含多條 Rule；一條 acceptance 場景可對應多個介面檔案、多個場景編號（如 BE-1.1、BE-1.2）。
- 場景標題必須描述**這組資料情境與被測動作**，不得重述 Rule 主張全文（見 Gherkin 階層與原子規則規範 Rule 3）。

## Good Example

```text
features/backend/送出聊天訊息.feature
features/backend/斷線重連聊天.feature
```

## Bad Example

```text
features/backend/聊天與對局.feature   # 一檔涵蓋整段旅程
```

# Rule 6 - 拆分後仍須完整覆蓋 acceptance 觀察

- 原子化不得刪除 acceptance 已鎖定的觀察事實；須改分配到適當的單一 `當` 場景與其 `那麼`。
- 若某觀察只出現在旅程終點（如完整六則對話表），須拆成多場景遞進 `Given 已有聊天訊息`，或分配給對應階段之主張場景；不得因原子化而跳過。
- 與**其他 Spec Package／介面**已覆蓋的領域（如 001 猜測結算明細）重疊時，介面 chat 場景可以高階 `Given` 表達對局狀態，只斷言與聊天直接相關的欄位。

## Good Example

- SBE-1 的「1234 不進猜測」：單場景 `當` 送出 1234，`那麼` 對話有列且 `猜測紀錄應該沒有紀錄`。

## Bad Example

- 砍掉所有 SBE-1 中介面場景，只留 acceptance，介面層零覆蓋。
