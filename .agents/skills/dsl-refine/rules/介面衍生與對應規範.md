# Rule 1 - 每個介面 Rule 與場景都必須保留來源對應

- 每條介面 `Rule` 上方必須以整行註解寫出來源驗收檔案與來源驗收主張。
- 每個介面 `場景` 或 `場景大綱` 上方必須以整行註解寫出來源驗收場景。
- 註解格式必須使用 `# 來源驗收檔案="..."`、`# 來源驗收主張="..."` 與 `# 來源驗收場景="..."`。
- 來源對應必須指向本次使用的 `features/acceptance/` 內容，不得指向舊介面 feature。
- 不得省略來源對應，否則之後無法回溯這條介面案例在驗證哪一條 acceptance。

## Good Example

- `Rule` 與 `場景` 都各自保留 acceptance 來源註解。

```gherkin
# language: zh-TW
功能: 送出房間聊天訊息

  # 來源驗收檔案="從房間聊到終局.feature"
  # 來源驗收主張="同一房間必須用同一串對話聊到終局且不改對局結果"
  Rule: 房間內兩位玩家都在時必須把送出的文字寫進聊天對話

    # 來源驗收場景="SBE-1 玩家A、玩家B、房間 2468，開局前聊到加入者猜中"
    場景: BE-1 房主送出有內容訊息
      假設 "房主" 與 "加入者" 已在房間 "2468"
      當 "房主" 對房間 "2468" 送出訊息 "等你"
      那麼 房間 "2468" 的聊天對話應該符合
        | 順序 | 發送者 | 內容 |
        | 1    | 房主   | 等你 |
```

## Bad Example

- 介面 `Rule` 與 `場景` 都沒有標示 acceptance 來源。

```gherkin
# language: zh-TW
功能: 送出房間聊天訊息

  Rule: 房間內兩位玩家都在時必須把送出的文字寫進聊天對話

    場景: BE-1 房主送出有內容訊息
      假設 "房主" 與 "加入者" 已在房間 "2468"
      當 "房主" 對房間 "2468" 送出訊息 "等你"
      那麼 房間 "2468" 的聊天對話應該符合
        | 順序 | 發送者 | 內容 |
        | 1    | 房主   | 等你 |
```

# Rule 2 - acceptance 場景可以拆分，但不得新增或改寫驗收行為

- 一個 acceptance 場景可以拆成多個介面 `Rule`、`場景` 或 `場景大綱`。
- 拆分後的每條介面案例必須仍在驗證原 acceptance 的既有主張、分支或觀察欄位。
- 拆分不得新增 acceptance 與 `spec.md` 都沒有的行為、拒絕原因、資料欄位或介面副作用。
- 拆分後的標題、步驟與 Data Table 必須符合 [介面原子粒度規範](介面原子粒度規範.md)，不得把 acceptance 長旅程原封不動搬下來。

## Good Example

- 同一 acceptance 場景拆成多條介面 Rule，各場景只有一個 `當`。

```gherkin
    # 來源驗收場景="SBE-1 玩家A、玩家B、房間 2468，開局前聊到加入者猜中"
    場景: BE-1.1 玩家A、玩家B、房間 2468、訊息等你
      假設 雙方已在大廳房間代碼 "2468"
      當 "玩家A" 對房間送出訊息 "等你"
      那麼 房間 "2468" 的聊天對話應該符合
        | 順序 | 發送者 | 內容 |
        | 1    | 房主   | 等你 |
```

## Bad Example

- 介面場景仍用 `當`＋多個 `而且` 串整段 acceptance 旅程。

```gherkin
    場景: BE-1 開局前聊到加入者猜中
      當 以下玩家送出房間代碼
      而且 "玩家A" 對房間送出訊息 "等你"
      而且 "房主" 要求開始對局
      而且 "房主" 送出猜測 "1347"
```

## Bad Example

- 拆分時新增了 acceptance 與 `spec.md` 都沒有的敏感詞審查規則。

```gherkin
    # 來源驗收場景="SBE-1 玩家A、玩家B、房間 2468，開局前聊到加入者猜中"
    場景: FE-1 房主送出髒話必須被遮罩
      假設 "房主" 的畫面已進入房間 "2468"
      當 "房主" 在房間 "2468" 送出訊息 "髒話"
      那麼 "加入者" 應該看見被遮罩的聊天訊息
```

# Rule 3 - 介面 feature 的每一句步驟都必須在同介面的 `dsl.md` 有對應句型

- 介面 feature 裡的每一句 `假設`、`當`、`那麼` 與 `而且`，都必須在同介面的 `dsl.md` 有對應句型。
- 同一個動作或觀察跨多個場景重複出現時，步驟文字必須相同，以便共用同一條 DSL 句型。
- 介面 feature 若改寫了一句步驟，同介面的 `dsl.md` 必須同步改寫對應句型。
- 不得先寫一批介面 feature，再把需要的句型留給之後猜測補完。

## Good Example

- feature 的 `當` 與 `那麼` 都能在同介面 `dsl.md` 找到同句句型。

```markdown
feature:
當 "房主" 對房間 "2468" 送出訊息 "等你"
那麼 房間 "2468" 的聊天對話應該符合

dsl:
| "{玩家角色}" 對房間 "{房間代碼}" 送出訊息 "{訊息內容}" | ... |
| 房間 "{房間代碼}" 的聊天對話應該符合 | ... |
```

## Bad Example

- feature 寫了新的步驟文字，但 `dsl.md` 沒有對應句型。

```markdown
feature:
當 "房主" 把訊息 "等你" 傳進房間 "2468"

dsl:
| "{玩家角色}" 對房間 "{房間代碼}" 送出訊息 "{訊息內容}" | ... |
```

# Rule 4 - 同一介面的 `.feature` 與 `dsl.md` 必須一起更新

- 當 acceptance 變動導致介面案例或句型需要調整時，該介面的 `.feature` 與 `dsl.md` 必須一起更新。
- 同一介面若新增了一個新動作、新觀察或新高階假設，必須同時寫進 `.feature` 與 `dsl.md`。
- 不得只更新其中一種 Artifact，讓另一種保留過時內容。

## Good Example

- 新增拒絕送出案例時，同步新增 feature 場景與 DSL 句型。

```text
features/backend/送出聊天訊息.feature
features/backend/dsl.md
```

## Bad Example

- 新增了後端 feature 場景，卻沒有更新同介面的 `dsl.md`。

```text
features/backend/送出聊天訊息.feature
```
