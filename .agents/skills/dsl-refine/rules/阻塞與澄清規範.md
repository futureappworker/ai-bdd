# Rule 1 - 權威來源已足夠時必須直接推導，不得先問偏好題

- acceptance 與 `spec.md` 已足以決定輸出時，必須直接產出介面 `.feature` 與 `dsl.md`。
- 既有 `features/<interface>/` 或既有 `dsl.md` 已提供不違反 acceptance 的技術入口、畫面元素或場景世界時，可以沿用。
- 不影響 acceptance 結果、且能用保守方式推導的缺口，應該直接採用保守推導，不得先向使用者追問風格或命名偏好。
- 不得為了檔名細節、章節順序、表格排版或可逆措辭差異中斷流程。

## Good Example

- acceptance 已規定「空白訊息必須拒絕」，既有後端 `dsl.md` 已有錯誤回應的檢查方式，因此直接產出拒絕案例。

```markdown
acceptance: 空白或只有空白字元的內容必須被拒絕
spec.md: 系統拒絕這次送出，雙方都不會多出一則訊息
existing backend dsl: 已有狀態碼與錯誤訊息的 Then 句型
```

## Bad Example

- acceptance 與 `spec.md` 都已足夠，卻先問使用者場景標題要寫 `BE-1` 還是 `Backend-1`。

```markdown
問題: 場景編號要寫 BE-1 還是 Backend-1?
```

# Rule 2 - 缺少介面落地所需的權威資訊時必須澄清並停止

- 經 `gherkin-and-dsl` 檢查後，若某個介面句型缺少 acceptance、`spec.md` 與既有介面文件都無法提供的必要資訊，必須向使用者澄清並停止本輪流程。
- 這類必要資訊包含技術入口、畫面操作入口、場景世界、回寫狀態、必要欄位對映，或會改變步驟定義契約的資料來源。
- 不得自行臆測這些資訊並把猜測寫入 `dsl.md`。
- 澄清問題必須只問阻塞該介面落地的最小必要決策。

## Good Example

- acceptance 只說「加入者看得到訊息」，但前端既有文件完全沒有聊天輸入框、送出按鈕或對話清單 test id，因此先停下來問前端入口。

```markdown
缺口: 前端 `dsl.md` 無法決定聊天輸入框與送出按鈕的技術入口
動作: 向使用者澄清前端畫面元素或測試入口，並停止本輪前端 DSL 生成
```

## Bad Example

- 前端入口完全缺失，卻自己捏造 `chat-input` 與 `chat-submit` 寫進 `dsl.md`。

```markdown
| "{玩家}" 在房間送出訊息 "{內容}" | ... `getByTestId("chat-input")` ... `getByTestId("chat-submit")` ... |
```

# Rule 3 - 可保守推導的非阻塞缺口應該以假設處理並繼續

- 當缺口不會改變 acceptance 結果，且可以用保守推導維持 `gherkin-and-dsl` 可落地性時，應該先完成 Artifact。
- 這類保守推導不得與 acceptance 或 `spec.md` 衝突。
- 若採用了保守推導，應該在回覆中告知使用者，而不是把它偽裝成已明示需求。
- 保守推導若在後續 `gherkin-and-dsl` 檢查中被判定仍不足以落地，必須回到前一條規則改為澄清。

## Good Example

- acceptance 沒指定後端 feature 要拆成一檔還是多檔，但主題可以依 Rule 主張拆成 `送出聊天訊息.feature`，不影響驗收結果，因此直接採用。

```markdown
acceptance: 已鎖定聊天送出與拒絕規則
spec.md: 未限制介面 feature 的檔案拆分方式
動作: 依 Rule 主張建立 `送出聊天訊息.feature`
```

## Bad Example

- acceptance 沒指定前端訊息清單如何定位，就把這個缺口當成「可保守推導」並隨意補一個 test id。

```markdown
| "{玩家}" 應該看見聊天訊息 | ... `getByTestId("message-list")` ... |
```
