# Rule 1 - 介面 Artifact 必須寫入同一個 Spec Package 的 `features/<interface>/`

- `dsl-refine` 產出的介面 `.feature` 與 `dsl.md` 必須寫入目標 `spec.md` 所屬 Spec Package 的 `features/<interface>/`。
- 使用者明確指定 `spec.md` 路徑時，必須使用該 Spec Package。
- 使用者未指定路徑，且 `specs/` 下只有一個 Spec Package 時，必須使用該 package。
- 使用者未指定路徑，且存在多個 Spec Package、又無法從本次輸入判斷時，必須停下請使用者指定，不得自行挑選。
- `features/<interface>/` 不存在時，必須建立該目錄後再寫入檔案。

## Good Example

- 介面 `.feature` 與 `dsl.md` 都落在同一個 Spec Package 的 `features/backend/`。

```text
specs/002-player-chat/spec.md
specs/002-player-chat/features/backend/送出聊天訊息.feature
specs/002-player-chat/features/backend/dsl.md
```

## Bad Example

- `dsl.md` 被寫回 Skill 目錄，沒有留在 Spec Package 裡。

```text
specs/002-player-chat/spec.md
.agents/skills/dsl-refine/templates/dsl.md
specs/002-player-chat/features/backend/送出聊天訊息.feature
```

# Rule 2 - 每個目標介面必須成對輸出 `.feature` 與 `dsl.md`

- 第一版預設介面必須包含 `backend` 與 `frontend`。
- 使用者有指定其他介面時，可以再額外建立 `features/<interface>/`。
- 每個目標介面必須同時產出至少一個 `.feature` 與一份 `dsl.md`。
- 這一步不得改寫 `features/acceptance/` 下的驗收 feature。
- 這一步不得只寫介面 `.feature` 而缺少同介面的 `dsl.md`，也不得只更新 `dsl.md` 而完全不對應介面 feature。

## Good Example

- `backend` 與 `frontend` 都各自成對輸出 `.feature` 與 `dsl.md`。

```text
specs/002-player-chat/features/backend/送出聊天訊息.feature
specs/002-player-chat/features/backend/dsl.md
specs/002-player-chat/features/frontend/送出聊天訊息.feature
specs/002-player-chat/features/frontend/dsl.md
```

## Bad Example

- 只寫後端 `dsl.md`，沒有任何後端 feature，也沒有前端輸出。

```text
specs/002-player-chat/features/backend/dsl.md
```

# Rule 3 - 權威順序必須是 acceptance 先於 spec 先於既有介面文件

- `features/acceptance/` 下的驗收 Gherkin 必須是最高權威來源。
- `spec.md` 必須作為 acceptance 的第二來源，用來補足 acceptance 未明寫但已在規格鎖定的資訊。
- 既有 `features/<interface>/` 與既有 `dsl.md` 只能被讀來對齊 acceptance 與 `spec.md`，不得反過來推翻它們。
- acceptance 與 `spec.md` 都沒有寫明、而既有介面文件自行新增的行為，不得被直接沿用為已確認需求。

## Good Example

- acceptance 已規定「房間只有一位玩家時不能送出」，介面 feature 只能對齊這個規則。

```markdown
acceptance: 房間只有一位玩家時不能送出訊息
spec.md: 房間只有一位玩家時，系統必須拒絕送出
backend feature: 房間只有一位玩家時，送出必須被拒絕
```

## Bad Example

- 舊的後端 feature 自行加入「單則超過 500 字」限制，但 acceptance 與 spec 都沒有這條，卻被當成權威需求保留。

```markdown
acceptance: 未提及訊息長度上限
spec.md: 未提及訊息長度上限
backend feature: 單則超過 500 字必須拒絕
```
