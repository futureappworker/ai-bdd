# Rule 1 - 結論必須分成必須修正與刻意保留

- 評估結論必須分別列出必須修正的項目與刻意保留的項目。
- 會讓場景無法單獨執行，或會讓步驟定義猜測技術入口、參數、寫回位置或斷言通道的項目，必須放在必須修正。
- 機械檢查的 `duplicate-step-text`，在兩句是同一個動作時，必須放在刻意保留，不得要求改寫其中一句。
- 機械檢查裡除了 `duplicate-step-text` 以外的錯誤，必須放在必須修正。
- 機械檢查未執行時，結論必須寫明未執行，不得把它當成通過。

## Good Example

- 同句的結帳留在刻意保留，缺入口的句子留在必須修正。

```markdown
必須修正:
- DSL 沒有「會員A 以配送地區結帳」的技術入口。

刻意保留:
- 「會員A 以配送地區結帳」在兩個場景大綱重複，對應同一個步驟定義。

結論: 還不能開始撰寫步驟定義。
```

## Bad Example

- 把刻意相同的步驟文字當成必須改寫，結論卻說可以開始寫程式。

```markdown
必須修正:
- 兩個場景的「以配送地區結帳」文字重複，請改成不同句子。

結論: 可以開始撰寫步驟定義。
```

# Rule 2 - 評估停止在結論

- 評估結論必須明確寫出「可以開始撰寫步驟定義」或「還不能開始撰寫步驟定義」。
- 還不能開始時，結論必須指出阻擋的 feature 與句子。
- 評估不得寫入步驟定義、測試程式或產品程式。
- 評估不得把來源案例標成不驗證的事項補成新步驟。

## Good Example

- 結論只判斷能不能寫步驟定義，沒有附上程式。

```markdown
結論: 還不能開始撰寫步驟定義。
阻擋: 結帳.feature 的「進行中的訂單應該有 0 筆」在 DSL 沒有再讀確認。
```

## Bad Example

- 評估同時寫出步驟定義，變成實作而不是評估。

```markdown
結論: 可以開始撰寫步驟定義。

When("{會員} 以配送地區 {region} 結帳") { ... }
```
