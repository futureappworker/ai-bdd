# Rule 1 - 每一句步驟都必須能寫成步驟定義

- feature 裡的每一句 `假設`、`當`、`那麼` 與 `而且`，都必須在 DSL 有對應句型。
- 每個句型必須寫明參數名稱、參數是字串或整數、有沒有 Data Table、Data Table 的欄位，以及預設值。
- 沒有預設值時必須寫明沒有預設。預設會改變 feature 的讀法時，feature 必須已有對應的 `# 參數="值"` 註解。
- 會發請求或操作介面的句子必須寫明技術入口、參數映射、上下文來源，以及寫回哪些場景狀態。
- 可能含前導零的商品編號或代碼，在 DSL 必須標成字串。
- DSL 缺任何一項，而步驟定義只能靠猜測補上時，該句不得視為可落地。

## Good Example

- 加入購物車這一句已經寫明入口、對應欄位、會員來源與寫回位置。

```markdown
| "{會員}" 把商品 "{商品編號}" 加入購物車 {數量} 件 | 會員與商品編號是字串，數量是整數 | 不支援 Data Table | 無預設 | POST /v1/cart/items；商品編號對 body.sku，數量對 body.quantity；會員來自 sessions[會員]；寫回 last_response，body 有 cartId 時寫回 cartId |
```

## Bad Example

- 句子只有中文，沒有入口與參數型別，步驟定義無法決定要打哪一支 API。

```markdown
| "{會員}" 把商品 "{商品編號}" 加入購物車 {數量} 件 | 把商品加入購物車並確認結果 |
```

# Rule 2 - When 只做動作

- `當` 的 DSL 不得寫斷言，也不得填斷言通道。
- `當` 必須把本次結果寫回場景狀態，包含失敗回應。
- 讀不到前置該寫入的身分或識別時，`當` 必須失敗，不得在 `當` 裡補做前置。

## Good Example

- 結帳只寫入回應，不檢查狀態碼。

```markdown
| "{會員}" 以配送地區 "{配送地區}" 結帳 | POST /v1/checkout；body.region 使用句中配送地區；寫回 last_response。不斷言 status。 |
```

## Bad Example

- `當` 的說明要求回應必須是 201，把斷言做進動作。

```markdown
| "{會員}" 以配送地區 "{配送地區}" 結帳 | 結帳，並確認狀態碼是 201、應付金額正確。 |
```

# Rule 3 - Then 必須寫明五個通道

- `那麼` 的每個句型都必須逐一寫明這五個通道：呈現結果、權威狀態、再讀確認、跨視角、不該發生。
- 某個通道不適用時，必須寫明不適用與原因，不得留空。
- 只有一位參與者時，跨視角必須寫明不適用。
- Data Table 句型必須寫明每一欄沿用哪一個單句的通道。沒有出現的欄位不得檢查。

## Good Example

- 件數這一句五個通道都有著落，跨視角寫明不適用的原因。

```markdown
| 購物車裡應該有 {件數} 件商品 | 呈現結果：回應的 totalQuantity 等於件數。權威狀態：cart_items 的數量總和等於件數。再讀確認：GET /v1/cart 的 totalQuantity 等於件數。跨視角：不適用，場景只有這位會員。不該發生：總和不得大於件數。 |
```

## Bad Example

- 只寫「確認件數正確」，五個通道都要靠步驟定義自行決定。

```markdown
| 購物車裡應該有 {件數} 件商品 | 確認件數正確。 |
```

# Rule 4 - 高階句子必須展開成既有句子

- 一個 `假設` 若代表一連串已存在的步驟，DSL 必須依序列出那些句子與帶入的參數。
- 高階句子不得引入尚未有句型的新動作。
- 與 `當` 文字相同的 `假設`，必須沿用該 `當` 的句型，不得另寫一套技術入口。

## Good Example

- 「購物車已有定價商品」依序展開成設定單價與庫存、再加入購物車。

```markdown
| 購物車已有定價商品 | 依序沿用：商品 "{商品編號}" 的單價是 {單價} 且庫存是 {庫存}；"{會員}" 把商品 "{商品編號}" 加入購物車 {數量} 件。不建立應用。 |
```

## Bad Example

- 高階句子只說「把購物車準備好」，沒有對應到已經定義的句子。

```markdown
| 購物車已有定價商品 | 直接把資料庫改成已有商品。 |
```
