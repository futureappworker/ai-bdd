# Rule 1 - 上游介面索引

- 案例引用到的每個上游介面必須在索引表各出現一次。
- 索引表必須包含介面、`plan.md` 盤點與契約三欄。
- 盤點欄必須指向 `plan.md` 系統介面盤點中已有的端點。
- 契約欄必須指向該介面的契約檔。
- 測試計劃不得重寫呼叫契約、公開介面清單、本介面涵蓋或留給其他介面。
- 案例的受測操作必須已經存在於該案例契約位址指向的契約檔。
- 測試計劃不得包含測試程式碼、SQL 或斷言函式呼叫。

## Good Example

- 索引只指向既有盤點與契約檔，案例另寫預期輸出。

```markdown
| 介面 | plan.md 盤點 | 契約 |
| --- | --- | --- |
| 後端房間 API | 系統介面盤點的後端端點「後端房間 API」 | `contracts/openapi.yaml` |
```

## Bad Example

- 同一介面改寫呼叫契約與公開操作清單，計劃變成第二份系統分析。

```markdown
**呼叫契約 ( Call Contract )**：進入成功回傳 `playerId`。
**公開介面 ( Public Interface )**：
- `POST /api/rooms/enter`
```

# Rule 2 - 使用者故事章與全域 NFR 章

- `spec.md` 的每一則使用者故事必須各成一章，並沿用該故事的標題與優先級。
- 使用者故事章必須全部排在全域 NFR 章之前。
- 有原子案例的每一條全域非功能需求必須各成一章。
- 全域 NFR 章的標題必須寫成 `全域 NFR - {需求編號} {需求名稱}`。
- 需求名稱必須能對到該條全域非功能需求。
- 全域 NFR 章的順序必須沿用這些需求在 `spec.md` 全域非功能需求中的相對順序。
- 沒有原子案例的全域非功能需求不得建立章。
- 全域功能需求與成功標準不得建立章。
- 測試計劃不得包含名為跨故事的章。

## Good Example

- 兩則使用者故事之後，NFR-G-001 與 NFR-G-003 各成一章。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

## 使用者故事 2 - 房主開始對局（Priority: P2）

## 全域 NFR - NFR-G-001 失敗後已進入的房間仍保留

### TDD 順序 ( Atomic Order )

#### 單元與服務測試

1. NFR-G-001

## 全域 NFR - NFR-G-003 房間讀取在 1 秒內回傳

### TDD 順序 ( Atomic Order )

#### 單元與服務測試

1. NFR-G-003
```

## Bad Example

- 同一組 NFR-G-001 與 NFR-G-003 被合成一個名為跨故事的章。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

## 使用者故事 2 - 房主開始對局（Priority: P2）

## 跨故事 - 房間資料可再讀

### TDD 順序 ( Atomic Order )

#### 單元與服務測試

1. NFR-G-001
2. NFR-G-003
```

# Rule 3 - 各章 TDD 順序

- 每個使用者故事章、每個全域 NFR 章，以及存在的總驗收章，必須各自有一份 TDD 順序。
- 該章 TDD 順序必須列出該章每個原子案例恰好一次。
- TDD 順序是該章的執行順序。
- 受測部位不含「瀏覽器」的案例必須全部排在 `#### 單元與服務測試`。
- 受測部位包含「瀏覽器」的案例必須全部排在 `#### 瀏覽器端到端測試`，且必須排在該章單元與服務測試之後。
- 某一段沒有案例時，必須省略該小標，不得留下空清單。

## Good Example

- 進房故事先列該章的服務案例，再列該章的瀏覽器案例。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

### TDD 順序 ( Atomic Order )

#### 單元與服務測試

1. BE-1.1
2. BE-3.1

#### 瀏覽器端到端測試

1. FE-1.1
```

## Bad Example

- 同一進房故事把瀏覽器案例排在服務案例之前，且沒有分成兩段。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

### TDD 順序 ( Atomic Order )

1. FE-1.1
2. BE-1.1
3. BE-3.1
```

# Rule 4 - 共用 Arrange Fixtures

- 兩個以上案例共用的前置狀態必須定義成共用 Arrange Fixture。
- Fixture 必須寫出可執行的前置操作，並保留後續呼叫需要的識別值。
- 案例的前置條件必須引用 Fixture 名稱。
- 只被一個案例使用的前置必須寫在該案例內，不得為它建立共用 Fixture。

## Good Example

- 兩個進房案例都引用已定義的空資料庫 Fixture。

```markdown
- **前置條件 ( Arrange )** Fixture 空資料庫。
```

## Bad Example

- 只有一個案例需要等待中的房主，卻把這段前置抽成共用 Fixture。

```markdown
1. **Fixture 等待房主**：玩家A 呼叫 `POST /api/rooms/enter`。
```

## Exceptions

- 案例要分辨的輸入與共用 Fixture 的字面值衝突時，該段前置寫在案例內。

# Rule 5 - 原子案例

- 一個案例必須只有一個唯一測試意圖。
- 一個案例要同時驗證兩個以上可分開觀察的結果時，必須拆成多個原子案例。
- 每個案例必須包含對應需求、契約位址、唯一測試意圖、受測部位、受測操作、前置條件、操作、觀測通道、預期輸出、必須維持不變、本案例不驗證、預期 RED 原因。
- 每個案例的契約位址必須只有一個，且必須是該案例受測操作的位址。
- 操作必須寫出這次送出的具體輸入，包含會影響規則判斷的字面值。
- 對應需求只索引規格。斷言要用的字面值必須寫在 Fixture、操作或預期輸出。

## Good Example

- 進房案例只指向進入房間這個操作，並寫出暱稱與房號。

```markdown
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
- **受測操作 ( Operation )** `POST /api/rooms/enter`
- **操作 ( Act )** `nickname` 為「玩家A」，`roomCode` 為「1234」。
```

## Bad Example

- 同一個案例同時要求建立房間、揭曉祕密答案與留下猜測紀錄。

```markdown
### BE-1.1 建立房間、揭曉祕密答案並留下猜測紀錄
```

## Exceptions

- 當案例對應的是 NFR 時，契約位址必須指向該品質需求所約束的既有操作。預期輸出必須寫規格原文已有的品質結果。不得要求契約另有一個 NFR 專用操作。

# Rule 6 - Oracle

- 預期輸出的每一項事實必須能對到該案例的觀測通道。
- 必須維持不變必須只列這次要斷言、且與操作前相同的欄位；沒有時必須寫「無」。
- 本案例不驗證列出的項目不得寫進預期輸出或必須維持不變。
- 每個案例必須寫預期 RED 原因，指出這個案例尚不存在時會失敗的觀察。

## Good Example

- 進房案例只斷言這次進入回應，並把祕密答案放在本案例不驗證。

```markdown
- **預期輸出 ( Expected Output )** HTTP 201。`role` 為房主。
- **必須維持不變 ( Must Stay )** 無。
- **本案例不驗證 ( Not Verified )** 祕密答案、猜測紀錄。
```

## Bad Example

- 本案例不驗證已排除祕密答案，預期輸出仍要求 `ownSecret`。

```markdown
- **預期輸出 ( Expected Output )** HTTP 201。`ownSecret` 為 5678。
- **本案例不驗證 ( Not Verified )** 祕密答案。
```

# Rule 7 - NFR 與不列為案例

- 規格原文已有可觀察結果的 NFR，必須寫成與 FR 相同欄位的原子案例。可觀察結果包含時間、數量、畫面上的狀態，或失敗後仍須保留的資料。
- 該 NFR 案例的契約位址必須指向被約束的既有操作。預期輸出必須寫該品質結果。
- 測試計劃不得替規格補上它沒寫的門檻、秒數、次數或文案。
- 屬於單一使用者故事的 NFR 案例必須放在該使用者故事章，並進入該章 TDD 順序。
- 全域 NFR 案例必須放在該需求自己的全域 NFR 章，並進入該章 TDD 順序。
- 一條全域 NFR 只有一個原子案例時，案例 ID 必須等於該需求編號。
- 一條全域 NFR 有多個原子案例時，每個案例 ID 必須以該需求編號開頭，並加上後綴，例如 `NFR-G-001-1`。這些案例 ID 必須在整份測試計劃唯一。
- 屬於單一使用者故事、且規格原文沒有可觀察結果的 NFR，必須在該章以 `### 不列為案例` 列出，並寫出原因。該章沒有這類項目時，必須省略這個小標。
- 沒有可觀察結果的全域 NFR，必須列在文件最後的 `## 不列為案例`。原因必須指出規格原文缺少時間、數量、可見狀態或失敗後仍須保留的資料。
- 全域功能需求必須列在文件最後的 `## 不列為案例`，不得寫成原子案例。原因必須指出它們不進入任務清單。
- 沒有任何文件層級不列為案例的項目時，必須省略 `## 不列為案例`。
- 不列為案例不得進入任何章的 TDD 順序。

## Good Example

- 規格寫了 1 秒內回傳，所以 NFR-G-003 自成一章並指向既有的讀取操作。FR-G-004 與使用者比例的成功標準列在文件最後的不列為案例。

```markdown
## 全域 NFR - NFR-G-003 房間讀取在 1 秒內回傳

### NFR-G-003 已存在的房間在 1 秒內回傳

- **對應需求 ( Traces )** NFR-G-003
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1{roomId}/get`
- **受測操作 ( Operation )** `GET /api/rooms/:roomId`
- **預期輸出 ( Expected Output )** 1 秒內 HTTP 200。

## 不列為案例

- **NFR-G-002**：玩家應感受到即時回饋。原因：規格原文只有感受描述，沒有時間、數量、可見狀態或失敗後仍須保留的資料。
- **FR-G-004**：已寫入的房間必須能由另一條連線讀回。原因：全域功能需求不進入任務清單。
- **SC-001**：90% 的玩家能在 1 分鐘內完成進房。原因：成功標準是使用者比例，沒有單次可觀察的系統結果。
```

## Bad Example

- 同一條 1 秒全域 NFR 因不屬於單一故事而被排除。FR-G-004 卻寫成跨故事章裡的原子案例。

```markdown
## 跨故事 - 房間資料可再讀

### BE-10.1 房間寫入後換一條資料庫連線仍讀得到同一場

- **對應需求 ( Traces )** FR-G-004
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1{roomId}/get`
- **受測操作 ( Operation )** `GET /api/rooms/:roomId`
- **預期輸出 ( Expected Output )** HTTP 200。

### 不列為案例

- **NFR-G-003**：已存在的房間在 1 秒內回傳。原因：不屬於單一使用者故事。
- **NFR-G-002**：玩家應感受到即時回饋。原因：規格原文只有感受描述，沒有時間、數量、可見狀態或失敗後仍須保留的資料。
- **SC-001**：90% 的玩家能在 1 分鐘內完成進房。原因：成功標準是使用者比例，沒有單次可觀察的系統結果。
```

# Rule 8 - 重複單元

- 介面、Fixture、使用者故事章、全域 NFR 章、總驗收章、案例與不列為案例的數量必須依上游輸入增減。
- 增減任一單元時，必須保留骨架中該單元的欄位與層級。
- 不得省略案例欄位，也不得新增骨架沒有的案例欄位。

## Good Example

- 需求只有一個故事與一個案例時，仍保留該案例的全部欄位。

```markdown
### BE-1.1 建立房間
- **對應需求 ( Traces )** FR-US1-001
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
- **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
- **受測部位 ( Subject )** 後端房間 API
- **受測操作 ( Operation )** `POST /api/rooms/enter`
- **前置條件 ( Arrange )** Fixture 空資料庫。
- **操作 ( Act )** `nickname` 為「玩家A」，`roomCode` 為「1234」。
- **觀測通道 ( Observation Channel )** 這次進入的回應。
- **預期輸出 ( Expected Output )** HTTP 201。`role` 為房主。
- **必須維持不變 ( Must Stay )** 無。
- **本案例不驗證 ( Not Verified )** 第二位玩家。
- **預期 RED 原因 ( Expected Red )** 進入回應不是 HTTP 201 的房主。
```

## Bad Example

- 案例只留下意圖與預期，省略契約位址、操作與預期 RED 原因。

```markdown
### BE-1.1 建立房間
- **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
- **預期輸出 ( Expected Output )** HTTP 201。
```

# Rule 9 - 畫面流程的受測部位是瀏覽器

- 使用者在畫面上完成的流程，受測部位必須包含「瀏覽器」。
- 該案例不得把受測部位寫成前端元件、前端畫面或其他不含「瀏覽器」的名稱。
- 該案例不得寫成可以 mock、替身或改接受測應用自己的 HTTP 或 WebSocket。
- 不開瀏覽器的案例，受測部位不得包含「瀏覽器」。

## Good Example

- 進房後要在畫面上看到等待對手，受測部位寫明瀏覽器，操作是按畫面上的按鈕。

```markdown
- **受測部位 ( Subject )** 瀏覽器對局畫面
- **受測操作 ( Operation )** 按「進入房間」
- **操作 ( Act )** 在「暱稱」填玩家A、在「房號」填 1234，按「進入房間」。
- **觀測通道 ( Observation Channel )** 畫面上的「房間狀態」。
```

## Bad Example

- 同一進房畫面改測前端元件，並允許 mock WebSocket。

```markdown
- **受測部位 ( Subject )** 前端對局畫面
- **受測操作 ( Operation )** 渲染進入房間後的元件
- **操作 ( Act )** 以 mock WebSocket 注入已進入房間的狀態。
- **觀測通道 ( Observation Channel )** 元件上的房間狀態文字。
```

# Rule 10 - 總驗收章

- 使用者故事有兩則以上，且這些故事能在同一次瀏覽器操作中先後完成時，必須在全部全域 NFR 章之後建立一章，標題為 `## 總驗收`。
- 沒有全域 NFR 章時，總驗收章必須直接排在最後一則使用者故事章之後。
- 只有一則使用者故事，或這些故事無法在同一次瀏覽器操作中先後完成時，不得建立總驗收章。
- 總驗收章必須包含一條案例 ID 為 `ACC-1` 的案例。
- `ACC-1` 的受測部位必須包含「瀏覽器」。
- `ACC-1` 的前置條件必須沿真實畫面完成較早的使用者故事。
- `ACC-1` 的預期輸出必須只斷言這條旅程的終點。
- `ACC-1` 不得重寫其他案例已經斷言的品質門檻，包含時間、數量、失敗後保留的資料與同時性。
- 成功標準描述的系統結果尚未被任何既有原子案例斷言，且該結果可在畫面上單次觀察時，必須在總驗收章追加案例。
- 追加案例的 ID 必須從 `ACC-2` 起連續編號。
- 成功標準是使用者比例、問卷或感受，或已被既有案例覆蓋時，必須留在文件最後的 `## 不列為案例`，並寫出原因。
- 全域功能需求不得寫成總驗收案例。
- 總驗收案例的預期 RED 原因必須寫出旅程終點不成立時的觀察。

## Good Example

- 兩則故事與全域 NFR 之後有一條瀏覽器旅程。使用者比例的成功標準留在不列為案例。

```markdown
## 全域 NFR - NFR-G-003 房間讀取在 1 秒內回傳

## 總驗收

### TDD 順序 ( Atomic Order )

#### 瀏覽器端到端測試

1. ACC-1

### ACC-1 兩位玩家從進房到開始對局後雙方仍看到輪到房主

- **受測部位 ( Subject )** 瀏覽器對局畫面
- **前置條件 ( Arrange )** 兩位玩家在畫面上完成進房與準備。尚未按「開始對局」。
- **預期輸出 ( Expected Output )** 雙方的房間狀態都是「對局中」。雙方的輪到都是「房主」。
- **本案例不驗證 ( Not Verified )** 1 秒、失敗後保留房間。

## 不列為案例

- **SC-001**：90% 的玩家能在 1 分鐘內完成進房。原因：成功標準是使用者比例，沒有單次可觀察的系統結果。
```

## Bad Example

- 同一組故事把跨故事旅程排除，沒有總驗收章。

```markdown
## 全域 NFR - NFR-G-003 房間讀取在 1 秒內回傳

## 不列為案例

- **SC-001**：90% 的玩家能在 1 分鐘內完成進房。原因：成功標準是使用者比例，沒有單次可觀察的系統結果。
- **SC-002**：雙方從進房到開始後都看得到輪到房主。原因：成功標準不進入任務清單。
```
