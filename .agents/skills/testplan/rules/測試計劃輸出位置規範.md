# Rule 1 - 目標路徑

- 使用者指定輸出路徑時，必須把測試計劃寫入該路徑。
- 輸入來源包含 `specs/<feature>/spec.md` 且使用者未指定輸出路徑時，必須寫入 `specs/<feature>/testplan.md`。
- 不得覆寫 `.agents/skills/testplan/templates/testplan.md` 或 `.agents/skills/testplan/templates/testplan.example.md`。

## Good Example

- 規格在 feature 目錄內，且使用者沒有另指定路徑，因此測試計劃寫在同一目錄。

```text
Input: specs/001-online-pvp-1a2b/spec.md
Output: specs/001-online-pvp-1a2b/testplan.md
```

## Bad Example

- 同一份規格的測試計劃被寫進 Template 範例，覆寫了已確認的 Artifact Example。

```text
Input: specs/001-online-pvp-1a2b/spec.md
Output: .agents/skills/testplan/templates/testplan.example.md
```

# Rule 2 - 獨立檔案

- 測試計劃必須是一份獨立檔案。
- 不得把測試計劃的介面索引、Fixture、案例或 TDD 順序寫進 `spec.md`、`plan.md` 或契約檔。

## Good Example

- 規格與系統分析維持原檔，測試計劃另存一份。

```text
specs/001-online-pvp-1a2b/spec.md
specs/001-online-pvp-1a2b/plan.md
specs/001-online-pvp-1a2b/testplan.md
```

## Bad Example

- 測試案例被追加在規格檔的章節裡，沒有獨立的測試計劃檔。

```text
specs/001-online-pvp-1a2b/spec.md
  ## 測試案例
```

# Rule 3 - 上游輸入

- 制定測試計劃前必須讀取同一功能的 `spec.md`、`plan.md`，以及 `plan.md` 產出契約列出的契約檔。
- `spec.md`、`plan.md` 或案例要引用的契約檔缺少時，必須把缺少的輸入寫入回覆並停止寫入 `testplan.md`。
- 不得在缺少上游輸入時自行新增介面、操作或畫面 frame。

## Good Example

- 規格、系統分析與 OpenAPI 都在，測試計劃才寫入同一功能目錄。

```text
Input: specs/001-online-pvp-1a2b/spec.md
Input: specs/001-online-pvp-1a2b/plan.md
Input: specs/001-online-pvp-1a2b/contracts/openapi.yaml
Output: specs/001-online-pvp-1a2b/testplan.md
```

## Bad Example

- 功能目錄還沒有 `plan.md`，測試計劃仍寫入並自訂一組 API。

```text
Missing: specs/001-online-pvp-1a2b/plan.md
Output: specs/001-online-pvp-1a2b/testplan.md
```
