# Rule 1 - 受測部位是瀏覽器就必須使用 Playwright

- 測試計劃案例或使用者需求中的受測部位包含「瀏覽器」時，必須把該接縫定為瀏覽器端到端。
- 瀏覽器端到端測試必須使用 Playwright 撰寫與執行。
- 不得改用 Vitest、jsdom、Testing Library 或元件渲染代替該接縫的測試。
- 不得因測試計劃寫了可以 mock、替身或接後端擇一，而改用行程內測試。

## Good Example

- 受測部位寫明瀏覽器，測試用 Playwright 開啟頁面並操作。

```typescript
test("輸入房間碼後進入大廳", async ({ page }) => {
  // Arrange
  await page.goto("/");

  // Act
  await page.getByLabel("房間碼").fill("1234");
  await page.getByRole("button", { name: "輸入房間碼並進入" }).click();

  // Assert
  await expect(page.getByRole("heading", { name: "房間 1234" })).toBeVisible();
});
```

## Bad Example

- 同一瀏覽器受測部位改在 jsdom 裡渲染元件，並用假的 fetch 跳過畫面操作。

```typescript
vi.stubGlobal("fetch", vi.fn(async () => new Response(JSON.stringify({ roomCode: "1234" }))));
render(<App />);
expect(await screen.findByText("房間 1234")).toBeInTheDocument();
```

# Rule 2 - 操作與斷言都在畫面上

- Act 必須是對真實頁面的操作，例如點擊、輸入與等待可見結果。
- 斷言必須只檢查畫面上看得到的文字、輸入框、按鈕狀態或同等可見結果。
- 案例要兩位使用者同時操作時，必須使用兩個瀏覽器上下文。
- 不得斷言元件內部狀態、函式回傳值或未出現在畫面上的物件。

## Good Example

- 輪到自己時，斷言畫面上看得到猜測輸入框。

```typescript
await expect(page.getByTestId("match-state")).toHaveText("輪到你猜");
await expect(page.getByTestId("guess-input")).toBeVisible();
```

## Bad Example

- 同一回合行為改斷言 match 物件的 currentTurnPlayerId，畫面上沒有對應操作。

```typescript
expect(match.currentTurnPlayerId).toBe("player-a");
```

# Rule 3 - 受測應用自己的通道必須留在真實程序

- 不得替換受測應用自己的頁面、HTTP 或 WebSocket。
- 第三方服務、時鐘與隨機性仍必須在邊界替換。
- 紅燈、綠燈與重構檢查本輪測試時，執行輸出必須來自 Playwright 測試指令。
- 專案尚未提供 Playwright 測試指令時，紅燈的失敗原因必須是該 Playwright 測試尚不可執行，不得改寫成行程內測試來取得失敗輸出。

## Good Example

- 猜測流程讓頁面打到受測應用自己的後端，不斷言被替換的 socket。

```typescript
await page.getByTestId("guess-input").fill("1234");
await page.getByRole("button", { name: "送出猜測" }).click();
await expect(page.getByTestId("guess-history")).toContainText("1A2B");
```

## Bad Example

- 同一猜測流程把 WebSocket 換成假物件，頁面沒有連到受測應用。

```typescript
vi.stubGlobal("WebSocket", class { send() {} });
render(<MatchPage match={fakeMatch} />);
```
