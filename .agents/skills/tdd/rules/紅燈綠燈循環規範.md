# Rule 1 - 先觀察失敗再寫實作

- 本輪必須先有一條測試，並用專案既有的測試指令執行它。
- 實作檔不得在該測試的執行輸出顯示失敗之前修改。
- 執行輸出必須顯示這條測試失敗，且失敗原因是本輪要建立的行為尚不存在。
- 沒有執行輸出時，必須把本輪測試視為不符合此規則。

## Good Example

- 測試先執行並失敗，失敗原因是結帳行為尚不存在。

```text
npm test -- checkout
FAIL user can checkout with valid cart
checkout is not defined
```

## Bad Example

- 同一條結帳測試尚未執行，實作檔已經寫入結帳邏輯。

```typescript
export async function checkout(cart, paymentMethod) {
  return { status: "confirmed" };
}
```

## Exceptions

- 當本輪接縫的受測部位是瀏覽器時，必須改以 Playwright 測試指令執行本輪測試，不得改用行程內測試指令。

# Rule 2 - 實作只覆蓋本輪測試

- 本輪實作不得加入本輪測試沒有要求的行為、分支或參數。

## Good Example

- 實作只回傳本輪測試要求的確認狀態。

```typescript
export async function checkout() {
  return { status: "confirmed" };
}
```

## Bad Example

- 同一輪實作同時加入空購物車分支，該行為沒有本輪測試要求。

```typescript
export async function checkout(cart) {
  if (cart.items.length === 0) {
    return { status: "rejected" };
  }
  return { status: "confirmed" };
}
```

# Rule 3 - 綠燈階段停止結構調整

- 最小實作完成後，必須用專案既有的測試指令再執行本輪測試。
- 執行輸出必須顯示本輪測試通過。
- 紅燈與綠燈階段不得重整既有結構、重新命名或搬移職責。
- 結構調整必須留到重構階段，並依 [重構循環規範](rules/重構循環規範.md) 執行。

## Good Example

- 綠燈階段只做到本輪測試通過，提取 priceCart 留到重構階段。

```text
綠燈階段結束
npm test -- checkout
PASS user can checkout with valid cart
```

## Bad Example

- 仍在綠燈階段就把結帳職責拆成新的內部模組。

```typescript
export async function checkout(cart, paymentMethod) {
  return confirmOrder(priceCart(cart), paymentMethod);
}
```

## Exceptions

- 當專案既有測試指令無法只執行本輪測試時，必須執行該指令並在結果中識別本輪測試的通過或失敗。
- 當本輪接縫的受測部位是瀏覽器時，必須改以 Playwright 測試指令執行本輪測試，不得改用行程內測試指令。
