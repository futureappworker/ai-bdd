# Rule 1 - Planner Skill 必須由端點責任選擇

- 每個系統介面必須依端點責任選擇一個主要 Planner Skill。
- 前端端點、瀏覽器互動、畫面狀態、使用者流程與可用性需求必須委派給 `ui-ux-plan`。
- 後端端點、API、WebSocket、服務狀態機、授權判定與跨玩家同步需求必須委派給 `api-plan`。
- 資料庫端點、持久化、資料模型、查詢、快照與保留期限需求必須委派給 `data-plan`。
- 端點責任無法判斷或同時跨多個主要責任且缺少主從關係時，必須委派給 `clarify` 產生澄清問題。

## Good Example

- 端點依主要責任選擇具名 Planner Skill。

```markdown
- 系統介面：瀏覽器前端互動介面
- 端點類型：前端端點
- Planner Skill：ui-ux-plan
```

## Bad Example

- 端點只寫「小 Skill」，沒有指定可執行的委派目標。

```markdown
- 系統介面：瀏覽器前端互動介面
- 端點類型：前端端點
- Planner Skill：小 Skill
```

# Rule 2 - Wave 執行必須遵守規劃順序

- Wave 必須依 `plan.md` 的分析流程安排順序執行。
- 同一個 Wave 內的端點可以平行委派給對應 Planner Skill。
- 後續 Wave 必須取得前序 Wave 的必要分析結果後才能執行。
- 不得因為 Planner Skill 名稱相同就跨 Wave 合併執行。

## Good Example

- 前端端點在 Wave 1 完成後，後端端點才取得前端結果並進入 Wave 2。

```markdown
#### Wave 1：前端端點
- Planner Skill：ui-ux-plan

#### Wave 2：後端端點
- Planner Skill：api-plan
```

## Bad Example

- 後端端點被提前與前端端點合併執行，破壞 Wave 依賴。

```markdown
#### Wave 1：前端端點與後端端點
- Planner Skill：ui-ux-plan
- Planner Skill：api-plan
```

# Rule 3 - 委派輸入必須保留需求追溯

- 委派給 Planner Skill 的內容必須包含系統介面名稱、端點類型、需求依據、介面定位與所在 Wave。
- 後續 Wave 的委派內容必須包含前序 Wave 中會影響該介面的分析結果。
- Planner Skill 不得只收到端點名稱而缺少需求依據。
- Planner Skill 回報的分析結果必須能追溯到原系統介面。

## Good Example

- 委派內容保留原始需求依據與 Wave 資訊。

```markdown
- 系統介面：即時房間與對局服務介面
- 端點類型：後端端點
- 所在 Wave：Wave 2
- 需求依據：FR-G-001 要求雙方介面狀態一致，FR-US1-001 要求只接受當前回合的合法猜測。
- 上游結果：Wave 1 已確認玩家會在對局畫面提交猜測並查看 A/B 紀錄。
```

## Bad Example

- 委派內容只保留端點名稱，Planner Skill 無法追溯需求。

```markdown
- 請分析後端。
```

# Rule 4 - 澄清必須在錯誤委派前發生

- 當端點類型、需求依據、Planner Skill 選擇或 Wave 依賴不足以判斷時，必須先委派 `clarify`。
- 當 Planner Skill 回報核心缺口會影響介面邊界或分析結論時，必須先委派 `clarify`。
- 不得把未知端點硬塞給最相近的 Planner Skill。
- 不得用假設補齊會影響介面責任邊界的缺口。

## Good Example

- 端點同時涉及第三方服務與資料持久化，且需求未說明主要責任，因此先澄清。

```markdown
- 缺口：付款紀錄由第三方保存還是本系統資料庫保存不明。
- 委派目標：clarify
```

## Bad Example

- 在主要責任不明時直接委派給資料 Planner，可能造成錯誤邊界。

```markdown
- 缺口：付款紀錄保存責任不明。
- 委派目標：data-plan
```
