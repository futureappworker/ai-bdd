# Rule 1 - 系統介面盤點必須從需求部位推導

- 系統介面盤點必須先讀取使用者需求原文或 Feature Specification，再從需求中可辨識的功能部位推導技術端點。
- 每個系統介面項目必須包含介面名稱、端點類型、需求依據與介面定位。
- 需求依據必須指出對應的需求原文片段或可追溯的需求內容。
- 端點類型必須描述技術端點類別，例如前端端點、後端端點、資料庫端點、手機端點、硬體端點、雲端端點或第三方服務端點。
- 不得只依常見架構慣例列出端點而缺少需求依據。

## Good Example

- 介面由需求原文的功能部位推導，且明確標示端點類型與需求依據。

```markdown
1. **付款服務介面**
   - 端點類型：第三方服務端點
   - 需求依據：需求原文提到使用者需要「完成信用卡付款」與「查詢付款狀態」。
   - 介面定位：第三方金流服務負責授權付款、回傳付款狀態與提供交易識別資訊。
```

## Bad Example

- 只列出常見端點，沒有從需求部位推導，也缺少需求依據。

```markdown
1. **付款服務介面**
   - 端點類型：第三方服務端點
   - 介面定位：系統應該要有付款服務。
```

# Rule 2 - 分析流程安排必須以端點為 Wave 單位

- 分析流程安排必須把每個 Wave 視為一組可以平行分析的技術端點。
- 每個 Wave 項目必須列出要委派的 Sub-agent 或具名 Planner Skill 分析哪一個系統介面。
- 每個被安排的端點必須對應系統介面盤點中的一個介面。
- 每個被安排的端點必須列出可執行的 Planner Skill 名稱，不得只寫泛稱的小 Skill。
- Wave 內不得放入不是端點的抽象工作，例如跨介面一致性檢查、整理報告或總結風險。
- 不得在分析流程安排中寫入實際系統分析結果。

## Good Example

- Wave 直接安排技術端點，且每個端點對應一個可委派的介面分析。

```markdown
#### Wave 1：前端端點與第三方金流端點

- Sub-agent 1：委派小 Skill 分析 **前端使用者互動介面**。
  - 端點類型：前端端點
  - Planner Skill：ui-ux-plan
  - 需求依賴判斷：前端操作流程會影響後端 API 的資料交換，因此先分析。
- Sub-agent 2：委派小 Skill 分析 **付款服務介面**。
  - 端點類型：第三方服務端點
  - Planner Skill：api-plan
  - 需求依賴判斷：付款服務主要依第三方文件與付款需求分析，和前端 UI 流程耦合度較低，可以平行處理。
```

## Bad Example

- Wave 放入抽象檢查工作，而不是技術端點本身。

```markdown
#### Wave 1：介面整理

- 整理前端與後端的需求。
- 檢查跨介面資料流是否一致。
```

# Rule 3 - Wave 排程必須說明需求依賴判斷

- 每個 Wave 必須包含 Wave 排程理由。
- 每個端點在 Wave 中必須包含需求依賴判斷。
- 需求依賴判斷必須說明該端點為何需要先分析、後分析或可與同 Wave 端點平行分析。
- 當端點和其他需求部位耦合度較低時，可以安排在較早 Wave 平行分析，但必須說明低耦合的理由。
- 不得只用技術層級或檔案順序決定 Wave。

## Good Example

- 排程理由清楚說明前端先行、第三方服務可平行、後端與資料庫放後面的需求依賴關係。

```markdown
#### Wave 1：前端端點與第三方金流端點

- Sub-agent 1：委派小 Skill 分析 **前端使用者互動介面**。
  - 端點類型：前端端點
  - Planner Skill：ui-ux-plan
  - 需求依賴判斷：多數需求先出現在使用者操作流程中，前端分析結果會影響後端 API 的資料交換。
- Sub-agent 2：委派小 Skill 分析 **付款服務介面**。
  - 端點類型：第三方服務端點
  - Planner Skill：api-plan
  - 需求依賴判斷：付款服務主要依第三方文件與付款狀態需求分析，可以和前端平行。
- Wave 排程理由：前端先確定使用者操作輪廓；付款服務和 UI 流程耦合度較低，因此同 Wave 平行。
```

## Bad Example

- 排程只列出端點順序，沒有說明需求依賴判斷。

```markdown
#### Wave 1

- 前端端點
- 金流端點

#### Wave 2

- 後端端點
- 資料庫端點
```
