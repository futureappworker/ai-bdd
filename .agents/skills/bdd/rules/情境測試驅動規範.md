# Rule 1 - 一次只推進一個情境

- 進入測試驅動後、撰寫第一個紅燈前，必須先以整個 feature 的命令做一輪預期為「盤點」的執行。
- 已經有這份 feature 的盤點結果時，不得再把預期設成「盤點」來取代下一個未通過情境的紅燈。
- 盤點只記錄每個情境是通過、失敗或步驟未定義，不得把尚未撰寫的 step definition 當成待修產品程式。
- 一個 `場景` 或一個 `場景大綱`（含全部 `例子` 列）是一個測試驅動單位。
- 一輪必須只為一個尚未通過的單位寫入紅燈。
- 必須依 feature 由上到下選擇下一個尚未通過的單位。
- 已通過的單位不得重寫，除非後續整個 feature 的執行證明它回歸失敗。
- 情境標題含正則特殊字元時，傳給執行器的名稱篩選必須跳脫，使它只命中該標題。
- 不得為了篩選執行而修改已接受的 feature，包括不得臨時加 Tag。

## Good Example

- 盤點後只把第一個未通過場景寫成會失敗的測試。

```text
盤點：場景「提取 40」步驟未定義；場景「餘額不足」步驟未定義。
本輪只寫「提取 40」的 step definition。
```

## Bad Example

- 尚未盤點，就把兩個場景的產品行為一起寫完。

```text
account.withdraw 已同時實作成功提領與餘額不足。
```

# Rule 2 - 紅燈只接線到產品邊界

- step definition 必須使用 Cucumber Expression，不得在同一個表達式混用正則。
- 註冊表達式時不得包含步驟關鍵字；`而且` 與 `但是` 沿用已註冊的同一句文字。
- 表達式必須全域唯一。
- `假設` 必須直接建立句子描述的狀態，不得呼叫這次 `當` 所驗證的那個動作來湊出狀態。
- `當` 必須呼叫這次情境鎖定的產品邊界，例如 domain service、HTTP client 或 browser driver。
- `那麼` 必須斷言該邊界回傳或顯示的、句子已點名的輸出。
- 產品行為必須寫在產品模組，不得寫進 step definition。
- 本輪尚未寫產品行為前，執行結果必須失敗。
- 正確紅燈的失敗原因必須是斷言失敗，或產品邊界因為行為尚未實作而失敗。
- Undefined step、Ambiguous step、Gherkin parse error、`exitCode` 為 null、`timedOut` 為 true，都不得當作正確紅燈。
- 行為尚未存在時測試就通過，必須把行為從 step definition 移回產品邊界，再重新執行。
- 盤點或紅燈執行證明該行為原本就存在時，必須把該情境視為已通過，不得刪除產品程式來製造紅燈。
- 只實作本輪情境用到的步驟；不得為後面的情境預先寫 step definition。
- 跨步驟狀態必須放在該情境自己的 World 或 scenario-scoped 物件。
- 不得使用模組層級或 `static` 的可寫狀態在情境之間傳遞資料。
- Cucumber.js 讀取 World 時必須使用一般 `function`，不得使用箭頭函式。
- 重複的操作必須抽成一般函式，不得從一個 step definition 再呼叫另一句 Gherkin。
- Data Table 儲存格必須視為字串，數值轉換寫在 step definition。
- `場景大綱` 的 `<欄名>` 在匹配前就會被替換；表達式必須寫替換後的 `{int}`、`{string}` 或自訂 parameter type，不得寫 `<欄名>`。
- 自訂 parameter type 必須在引用它的 step definition 載入前註冊。

## Good Example

- `假設` 直接設定餘額，`當` 呼叫尚未完成的產品邊界，所以執行會失敗。

```javascript
Given("帳戶 {string} 的餘額是 {int}", function (id, balance) {
  this.accounts.setBalance(id, balance);
});

When("客戶從帳戶 {string} 提取 {int}", function (id, amount) {
  this.lastWithdrawal = this.accounts.withdraw(id, amount);
});

Then("帳戶 {string} 的餘額應該是 {int}", function (id, expected) {
  assert.equal(this.accounts.balanceOf(id), expected);
});
```

## Bad Example

- step definition 自己扣款並直接通過，產品邊界沒有這個行為。

```javascript
When("客戶從帳戶 {string} 提取 {int}", function (id, amount) {
  const account = this.accounts.get(id);
  account.balance -= amount;
  this.lastWithdrawal = { ok: true };
});
```

# Rule 3 - 沿用既有 Cucumber 佈局

- 專案已有 Cucumber 執行器、feature 目錄或 step definition 時，必須沿用該佈局與測試命令。
- 不得在已有 Cucumber 的專案另起第二套執行器。
- 專案還沒有 Cucumber 時，必須建立 Cucumber.js 佈局：`features/<name>.feature`、`features/step_definitions/<domain>_steps.js`、`features/support/`，以及會先載入 `features/support/**/*.js` 再載入 `features/step_definitions/**/*.js` 的 `cucumber.js`。
- 專案還沒有 Cucumber 時，測試命令必須是 `npx cucumber-js`，只跑一個情境時加上該執行器的名稱篩選。
- 專案還沒有 `@cucumber/cucumber` 時，必須把它加入開發依賴，讓測試命令可以執行。
- Cucumber-JVM 的狀態必須放在 scenario-scoped 物件，不得使用 `static` 欄位跨情境分享。

## Good Example

- 專案已經有 Cucumber-JVM，本輪沿用原 feature 路徑與 Maven 測試命令。

```text
沿用 src/test/resources/withdraw.feature。
本輪命令：mvn -Dtest=WithdrawTest test。
```

## Bad Example

- 專案已經有 Cucumber-JVM，卻另外新增一套 Cucumber.js。

```text
src/test/resources/withdraw.feature 已存在。
另外新增 features/withdraw.feature 與 cucumber.js。
```

# Rule 4 - 綠燈只補本情境的產品行為

- 只有正確紅燈出現後，才必須寫入產品行為。
- 產品修改必須只讓本輪這一個情境通過。
- 不得修改 feature。
- 不得刪除、註解或放寬 `那麼` 的斷言來換取通過。
- 預期「通過」時，結果檔的 `executed` 必須為 true、`timedOut` 必須為 false、`exitCode` 必須為 0。
- `exitCode` 為 null 或 `timedOut` 為 true 時，必須先修正命令或逾時，不得改產品程式。

## Good Example

- 紅燈是餘額未扣除後，才在產品模組補上提領行為。

```javascript
withdraw(id, amount) {
  const account = this.require(id);
  account.balance -= amount;
  account.transactions.push({ type: "withdraw", amount });
  return { ok: true };
}
```

## Bad Example

- 測試沒通過，於是把結果句的斷言從 step definition 移除。

```javascript
Then("帳戶 {string} 的餘額應該是 {int}", function () {
  return;
});
```

# Rule 5 - 通過後才重構重複的測試程式

- 本情境通過後，兩個 step definition 含有相同操作時，必須把該操作抽成一般函式再讓兩邊呼叫。
- 本情境通過後，step definition 仍含有產品行為、模組層級可寫狀態或箭頭函式的 World 存取時，必須先重構再進入下一輪。
- 沒有上述重複或職責錯放時，不得為了整理程式改動已通過的行為。
- 重構後必須再執行本情境，而且結果必須維持通過。
- 重構不得修改 feature，也不得放寬斷言。

## Good Example

- 兩個登入步驟通過後，共用一個一般函式。

```javascript
async function login(world, email, password) {
  await world.sessions.login(email, password);
}

When("使用者 {string} 以有效憑證登入", async function (email) {
  await login(this, email, this.passwords.for(email));
});

When("使用者 {string} 以密碼 {string} 登入", async function (email, password) {
  await login(this, email, password);
});
```

## Bad Example

- 兩個登入步驟各自複製同一段操作，沒有抽成一般函式。

```javascript
When("使用者 {string} 以有效憑證登入", async function (email) {
  await this.sessions.login(email, this.passwords.for(email));
});

When("使用者 {string} 以密碼 {string} 登入", async function (email, password) {
  await this.sessions.login(email, password);
});
```

# Rule 6 - 一個情境通過後必須繼續

- 還有未通過情境時，必須繼續下一個情境，不得在本情境通過後結束。
- 全部情境都通過後，必須再執行一次整個 feature，而且結果必須通過。
- 整個 feature 失敗時，必須修正造成回歸的產品程式，不得修改已接受的 feature。

## Good Example

- 第一個情境通過後繼續下一個未通過情境，最後再跑整個 feature。

```text
場景「提取 40」已通過。
下一個情境是「餘額不足」。
兩個情境都通過後，執行整個 features/withdraw.feature。
```

## Bad Example

- 第一個情境通過後就結束，後面的情境還沒有測試與產品行為。

```text
場景「提取 40」已通過。測試驅動完成。
```
