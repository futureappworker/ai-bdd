# Rule 1 - 一個情境只證明一件事

- 一個 `場景` 或一個 `場景大綱` 必須只證明一種行為。
- 情境標題必須是一句話，並且在同一個 feature 內唯一。
- 標題塞不進一句話時，必須拆成兩個情境。
- 有動作的情境必須剛好有一個 `當`。
- 第二個動作若是前置，必須改寫成 `假設`。
- 結果種類不同時，必須拆成不同情境，不得合成一個 `那麼 結果應該是 <result>`。
- 一個情境的步驟數應該是 3 到 5。
- 純狀態結論可以只有 `假設` 與 `那麼`。

## Good Example

- 成功提領與餘額不足拆成兩個場景，各自只有一個 `當`。

```gherkin
場景: 提取 40 後餘額是 60
  假設 帳戶 "A-1" 的餘額是 100
  當 客戶從帳戶 "A-1" 提取 40
  那麼 帳戶 "A-1" 的餘額應該是 60

場景: 餘額不足時拒絕提領
  假設 帳戶 "A-1" 的餘額是 20
  當 客戶從帳戶 "A-1" 提取 40
  那麼 提領應該被拒絕，原因是 "餘額不足"
```

## Bad Example

- 同一個場景先成功提領再因為餘額不足被拒，含有兩個 `當`。

```gherkin
場景: 提領成功與餘額不足
  假設 帳戶 "A-1" 的餘額是 100
  當 客戶從帳戶 "A-1" 提取 40
  那麼 帳戶 "A-1" 的餘額應該是 60
  當 客戶從帳戶 "A-1" 提取 80
  那麼 提領應該被拒絕，原因是 "餘額不足"
```

## Exceptions

- 當 `背景` 已經寫出該情境的前置，場景本體只剩一個 `當` 與一個 `那麼` 時，可以少於 3 個步驟。

# Rule 2 - 步驟只寫該層級的事實

- `假設` 必須是動作發生前已經成立的狀態。
- `當` 必須是這次要驗證的那一個動作或事件。
- `那麼` 必須是句子點名的可觀察輸出，例如回應內容、畫面文字、回傳值或訊息。
- `那麼` 必須帶有斷言對象的識別資訊。
- 句子沒有點名的內部資料，不得寫進 `那麼`。
- 一步必須只寫一件事。

## Good Example

- 結果句點名帳戶，並檢查提領後看得到的餘額。

```gherkin
那麼 帳戶 "A-1" 的餘額應該是 60
```

## Bad Example

- 結果句沒有識別資訊，執行時必須猜測是哪一個帳戶。

```gherkin
那麼 餘額應該是 60
```

# Rule 3 - 操作路徑留在程式

- URL、欄位名、按鈕文字、CSS、selector 與資料表欄位不得寫進 feature。
- 這些操作路徑必須留在 step definition 或它呼叫的 helper。
- 會改變本次斷言的輸入與預期輸出必須寫在 feature，例如金額、錯誤原因、錯誤密碼。
- 實作細節一換就必須改寫的句子，必須改寫成該操作完成的行為。

## Good Example

- feature 寫登入這件行為，密碼檔與欄位留在程式。

```gherkin
當 使用者 "free@example.com" 以有效憑證登入
```

## Bad Example

- feature 寫死登入頁的路徑、欄位與按鈕。

```gherkin
假設 使用者打開 "/login"
當 使用者在欄位 "email" 輸入 "free@example.com"
而且 使用者在欄位 "password" 輸入 "validPassword123"
而且 使用者按下 "送出"
```

# Rule 4 - 多筆資料用對應的 Gherkin 構造

- 同一串步驟只換值、而且每一組值都要單獨執行時，必須使用 `場景大綱` 與 `例子`。
- `<欄名>` 必須出現在該大綱的 `例子` 表頭。
- 表頭與 `<欄名>` 必須完全相同。
- `{string}` 需要的引號必須寫在步驟上，不得期待 `例子` 儲存格自動補引號。
- 只有一列資料時，必須使用一般 `場景`，把值直接寫進行列。
- 一個步驟要一次收下一批資料時，必須使用 Data Table，不得把那張表寫成 `場景大綱`。
- 一個步驟要收下一大段文字時，必須使用 Doc String。
- 一個步驟不得同時附上 Data Table 與 Doc String。

## Good Example

- 兩組金額各跑一次，占位符都能在表頭找到，引號寫在步驟上。

```gherkin
場景大綱: 成功提領後餘額正確
  假設 帳戶 "<id>" 的餘額是 <start>
  當 客戶從帳戶 "<id>" 提取 <amount>
  那麼 帳戶 "<id>" 的餘額應該是 <left>

  例子:
    | id  | start | amount | left |
    | A-1 | 100   | 40     | 60   |
    | A-1 | 100   | 100    | 0    |
```

## Bad Example

- 同一組步驟使用了表頭沒有的 `<left>`，執行前無法替換這個占位符。

```gherkin
場景大綱: 成功提領後餘額正確
  假設 帳戶 "<id>" 的餘額是 <start>
  當 客戶從帳戶 "<id>" 提取 <amount>
  那麼 帳戶 "<id>" 的餘額應該是 <left>

  例子:
    | id  | start | amount |
    | A-1 | 100   | 40     |
    | A-1 | 100   | 100    |
```

# Rule 5 - 背景只放每個情境都成立的前置

- `背景` 必須只放所屬 `功能` 或 `Rule` 底下每個情境都成立的 `假設`。
- `背景` 不得包含 `當` 或 `那麼`。
- 某個情境需要不同起點時，該前置必須留在該情境，不得寫進共用 `背景`。
- `背景` 應該不超過 4 行；超過時必須把讀者不必逐行知道的細節收成一個較高的 `假設`。
- 一個 `功能` 必須最多一個 `背景`，一個 `Rule` 必須最多一個 `背景`。
- 互斥結果必須分成不同 `Rule`，讓各自的 `背景` 不會套到對方身上。
- 每個情境，包含 `場景大綱` 的每一列，都必須能單獨、平行、調換順序執行。
- Tag 只能用來篩選執行或掛基礎設施 hook。
- 會影響斷言的業務前置必須寫成 `假設`，不得只放在 Tag 或 hook。

## Good Example

- 成功提領的共同餘額放在該 `Rule` 的背景，餘額不足另寫自己的起點。

```gherkin
Rule: 餘額足夠時扣除提領金額

  背景:
    假設 帳戶 "A-1" 的餘額是 100

  場景: 提取 40 後餘額是 60
    當 客戶從帳戶 "A-1" 提取 40
    那麼 帳戶 "A-1" 的餘額應該是 60

Rule: 餘額不足時拒絕提領

  場景: 餘額不足
    假設 帳戶 "A-1" 的餘額是 20
    當 客戶從帳戶 "A-1" 提取 40
    那麼 提領應該被拒絕，原因是 "餘額不足"
```

## Bad Example

- 餘額不足沿用餘額 100 的背景，沒有自己的起點。

```gherkin
Rule: 餘額足夠時扣除提領金額

  背景:
    假設 帳戶 "A-1" 的餘額是 100

  場景: 提取 40 後餘額是 60
    當 客戶從帳戶 "A-1" 提取 40
    那麼 帳戶 "A-1" 的餘額應該是 60

Rule: 餘額不足時拒絕提領

  場景: 餘額不足
    當 客戶從帳戶 "A-1" 提取 40
    那麼 提領應該被拒絕，原因是 "餘額不足"
```

# Rule 6 - 不得編造可觀察結果

- 需求沒有寫出的可觀察結果或條件，不得寫成 `那麼` 或 `假設`。
- 該缺口必須留在 Review 回覆，等待使用者補上。
- 已寫入 feature 的每個數值、原因與身份都必須能對回需求或使用者在 Review 中接受的句子。

## Good Example

- 需求只說會拒絕提領，feature 不斷言需求沒寫的錯誤代碼。

```gherkin
那麼 提領應該被拒絕
```

## Bad Example

- 需求沒寫原因文字，feature 仍斷言一個編造的原因。

```gherkin
那麼 提領應該被拒絕，原因是 "餘額不足"
```
