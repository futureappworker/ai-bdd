# Rule 1 - 使用時機與入口

- `bdd` 必須只在上游已產出且使用者已接受 `.feature` 之後使用；介面情境可來自 `dsl-refine`，驗收旅程可來自 `features/acceptance/`。
- 呼叫者必須明示本次子命令是 `red`、`green` 或 `refactor` 其中之一。
- 同一次執行必須只處理一個子命令，不得在 `bdd` 內部自動串接下一個子命令。
- 使用者或呼叫者要求產出、修改或 Review `.feature` 時，必須停止並指出該工作屬於上游 feature 產出流程或人工修改流程。

## Good Example

- 呼叫者已指定單一子命令，且 `.feature` 已先存在。

```text
implement -> bdd red
目標：specs/002-player-chat/features/backend/送出聊天訊息.feature
情境：房客送出一則聊天訊息
```

## Bad Example

- `bdd` 同時承接 feature 產出與三階段自動推進，已超出本 Skill 的新邊界。

```text
bdd 先產生 feature，接著自己依序跑 red、green、refactor。
```

# Rule 2 - Feature 是唯讀權威

- 目標 `.feature` 必須視為本輪測試驅動的唯讀權威輸入。
- `red`、`green` 與 `refactor` 期間不得修改 `.feature` 文字。
- 發現句子彼此衝突、缺少可落地事實或與產品邊界不相容時，必須停止並指出衝突句子。
- 停止後必須把修正責任交回上游 feature 產出流程或人工修改，不得由 `bdd` 代改 `.feature`。

## Good Example

- 發現 feature 句子無法同時成立時停止，沒有改寫權威來源。

```text
場景要求「訊息送出後應該保留在輸入框」與「訊息送出後應該清空輸入框」。
bdd 停止並回報衝突句子，沒有修改 feature。
```

## Bad Example

- 為了讓測試好寫而直接改寫權威來源。

```text
bdd 把「訊息送出後應該清空輸入框」改成「訊息送出後應該保留在輸入框」後再繼續。
```

# Rule 3 - 一次只處理一個測試驅動單位

- 呼叫者必須指定一個目標 `場景` 或一個目標 `場景大綱`。
- 一次執行必須只處理該目標單位，不得順便推進下一個未通過情境。
- 傳給執行器的名稱篩選必須只命中該標題；標題含正則特殊字元時必須先跳脫。
- 本輪結果路徑必須獨立存在，且不得覆寫 `.feature` 或產品程式。

## Good Example

- 呼叫者鎖定單一情境，執行命令也只命中該情境。

```text
子命令：green
情境：房客送出一則聊天訊息
命令：npx cucumber-js --name "^房客送出一則聊天訊息$"
```

## Bad Example

- 沒有鎖定單一情境，還讓 Skill 自己推斷下一個目標。

```text
先跑整個 feature 看哪個失敗，再由 bdd 自己決定接下來要做哪個情境。
```

# Rule 4 - 沿用既有測試佈局與命令

- 專案已有 Cucumber 執行器、feature 目錄或 step definition 時，必須沿用該佈局與測試命令。
- 專案已有 Cucumber 佈局時，不得另起第二套執行器。
- 專案還沒有 Cucumber 佈局時，可以建立最小必要的 Cucumber 佈局與可執行命令。
- 本輪命令必須能透過 `scripts/run-scenario.py` 產出可檢查的結果檔。

## Good Example

- 專案已有 Playwright + Cucumber 佈局時，沿用既有路徑與命令。

```text
沿用 frontend/features/ 與既有 npm test:cucumber 命令。
```

## Bad Example

- 專案已有既有 runner，卻平行新增另一套測試主幹。

```text
backend/features/ 已存在，bdd 另外再建立 tests/cucumber/ 與第二份 runner 設定。
```
