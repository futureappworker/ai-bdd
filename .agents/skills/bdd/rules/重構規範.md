# Rule 1 - 重構只處理測試程式

- `refactor` 階段必須只修改目標情境相關的 step definition、World 或測試 helper。
- `refactor` 階段不得修改 `.feature`。
- `refactor` 階段不得主動重構產品程式。
- 發現真正需要整理的是產品程式時，必須停止並指出該工作不在本次 `refactor` 邊界內。

## Good Example

- 只整理測試碼結構，產品行為保持不動。

```javascript
async function sendChat(world, playerId, message) {
  world.lastResponse = await world.chatClient.send(playerId, message);
}
```

## Bad Example

- 借重構之名同步改產品邏輯，已超出階段邊界。

```typescript
send(playerId: string, message: string) {
  this.auditTrail.push({ playerId, message });
  this.messages.push({ playerId, message });
  return { ok: true };
}
```

# Rule 2 - 重構目標是去重複與職責錯放

- `refactor` 階段前必須已有同一情境的最新通過證據。
- 重構應該以消除重複操作、收斂 World 狀態、移除模組層級可寫狀態或抽出一般 helper 為主。
- 不得從一個 step definition 直接呼叫另一句 Gherkin 來共用邏輯。
- 沒有重複或職責錯放時，可以不做重構，直接維持通過結果。

## Good Example

- 兩個步驟共用相同行為時，抽成一般 helper。

```javascript
async function login(world, playerId) {
  await world.sessions.login(playerId);
}
```

## Bad Example

- 直接從一個 step definition 呼叫另一個 step definition，沒有真正整理責任。

```javascript
When("玩家 {string} 重新登入", async function (playerId) {
  await this.runStep(`當 玩家 "${playerId}" 登入房間`);
});
```

# Rule 3 - 重構後必須維持通過

- `refactor` 後必須重跑同一個目標情境。
- 驗證結果必須同時滿足 `executed` 為 `true`、`timedOut` 為 `false`、`exitCode` 為 `0`。
- 重構後回歸失敗時，必須先修正測試程式，不得放寬斷言或回頭修改 `.feature`。
- 重構完成後必須停止，不得在同一次執行內自行跳到下一個情境。

## Good Example

- 重構後仍維持同一情境通過。

```json
{
  "executed": true,
  "exitCode": 0,
  "timedOut": false,
  "stdout": "1 scenario (1 passed)"
}
```

## Bad Example

- 重構後測試失敗，卻透過放寬斷言來掩蓋回歸。

```javascript
Then("玩家 {string} 應該看到聊天訊息 {string}", function () {
  return;
});
```
