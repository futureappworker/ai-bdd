# Rule 1 - 綠燈前必須已有有效紅燈

- `green` 階段前必須已有同一個目標情境的最新紅燈證據。
- 該紅燈證據必須符合有效失敗要求，否則不得寫入產品行為。
- 前一輪結果若對應不同情境、不同命令或不同 `.feature`，必須停止並指出證據不相符。
- 缺少紅燈證據時，必須要求呼叫者先執行 `bdd red`。

## Good Example

- 綠燈以前先確認同一情境已有正確紅燈。

```text
上一輪：bdd red
feature：specs/002-player-chat/features/backend/送出聊天訊息.feature
情境：房客送出一則聊天訊息
結果：AssertionError，exitCode 1，timedOut false
```

## Bad Example

- 沒有先確認紅燈證據，就直接開始補產品行為。

```text
呼叫者直接要求 bdd green，但沒有提供同一情境的最新紅燈結果。
```

# Rule 2 - 綠燈只補本情境的產品行為

- `green` 階段必須只修改讓本輪目標情境通過所需的產品模組。
- `green` 階段不得修改 `.feature`。
- `green` 階段不得放寬、刪除或註解 `那麼` 斷言來換取通過。
- `green` 階段不得順便實作後面情境尚未要求的行為。

## Good Example

- 只補上本輪情境需要的產品行為，沒有改動 feature 或測試斷言。

```typescript
send(playerId: string, message: string) {
  this.requireMember(playerId);
  this.messages.push({ playerId, message });
  return { ok: true };
}
```

## Bad Example

- 透過移除斷言來讓測試通過，不是合法綠燈。

```javascript
Then("玩家 {string} 應該看到聊天訊息 {string}", function () {
  return;
});
```

# Rule 3 - 綠燈結果必須通過

- `green` 執行結果必須同時滿足 `executed` 為 `true`、`timedOut` 為 `false`、`exitCode` 為 `0`。
- `exitCode` 為 `null` 或 `timedOut` 為 `true` 時，必須先修正命令或環境問題，不得把問題歸咎於產品程式。
- 綠燈失敗時，必須修正產品程式，不得回頭改寫已接受的 `.feature`。
- 本輪情境已通過時，必須停止並把是否進入 `refactor` 交給呼叫者決定。

## Good Example

- 綠燈結果明確通過，且交還下一步決定權給呼叫者。

```json
{
  "executed": true,
  "exitCode": 0,
  "timedOut": false,
  "stderr": "",
  "stdout": "1 scenario (1 passed)"
}
```

## Bad Example

- 逾時不是產品邏輯通過，不能當成綠燈完成。

```json
{
  "executed": true,
  "exitCode": null,
  "timedOut": true,
  "stderr": ""
}
```
