# Rule 1 - 增量只寫一份產出

- 寫入目標是產出憲法時，必須寫入 `constitution/<skill>/<artifact>.md`。
- 產出憲法的檔頭必須標明 Skill 與產出路徑。
- 產出路徑含角括號時，必須放在行內程式碼。
- 本次不得建立使用者尚未確認的其他憲法檔。

## Good Example

- 使用者確認的是 OpenAPI 成功回應，因此只寫入對應的那一份憲法。

```text
constitution/api-plan/openapi.yaml.md
```

## Bad Example

- 同一次增量另外建立使用者尚未確認的 DBML 憲法。

```text
constitution/api-plan/openapi.yaml.md
constitution/data-plan/schema.dbml.md
```

# Rule 2 - 一條 Rule 只約束一個部位

- 本次必須只新增或修改使用者確認的那一條 Rule。
- 同一檔內未被本次確認的 Rule 必須保持不變。
- 這條 Rule 必須寫明一個部位。
- 這個部位不得與同一檔既有 Rule 的部位相同。
- 部位相同時，必須停止寫入並在回覆回報衝突的兩條 Rule。
- 要求新增流程階段、改寫 Skill 順序或約束原始碼的內容不得寫入憲法檔。

## Good Example

- 既有 Rule 1 約束成功回應 schema，本次新增的 Rule 2 改約束錯誤回應 schema。

```markdown
# Rule 1 - I. 成功回應信封

- 部位必須是 HTTP 成功回應所引用的 JSON schema。

# Rule 2 - II. 錯誤回應信封

- 部位必須是 HTTP 錯誤回應所引用的 JSON schema。
```

## Bad Example

- 本次新增的 Rule 2 與 Rule 1 約束同一個成功回應 schema。

```markdown
# Rule 1 - I. 成功回應信封

- 部位必須是 HTTP 成功回應所引用的 JSON schema。

# Rule 2 - II. 成功回應識別碼

- 部位必須是 HTTP 成功回應所引用的 JSON schema。
```

## Exceptions

- 寫入動作是基本版時，不適用「本次必須只新增或修改使用者確認的那一條 Rule」。
- 寫入動作是基本版時，不得以「這條 Rule 必須寫明一個部位」、流程改寫或原始碼約束拒絕寫入。

# Rule 3 - 條文必須能被檢查

- Rule 標題必須使用 `# Rule N - <羅馬數字>. <名稱>`。
- 新檔的第一條必須是 `Rule 1` 與 `I.`。
- 既有檔的下一條編號必須接在最後一條之後，且羅馬數字必須與編號同步。
- 約束條列必須使用「必須」或「不得」。
- 每一條 Rule 必須包含成對的 Good Example 與 Bad Example。
- Good Example 與 Bad Example 必須描述同一情境，且案例必須放在有語言標記的 Code Section。

## Good Example

- 新檔的第一條從 Rule 1 與 I. 開始，Good Example 與 Bad Example 描述同一則功能需求。

```markdown
# Rule 1 - I. 規格敘述使用繁體中文

- 部位必須是功能需求的敘述文字。
- 這些敘述文字必須使用繁體中文。

## Good Example

- 同一則功能需求的敘述使用繁體中文。

## Bad Example

- 同一則功能需求的敘述只有英文。
```

## Bad Example

- 標題沒有羅馬數字，也沒有成對的 Example。

```markdown
# Rule 1 - 規格要清楚

- 規格盡量使用中文。
```

# Rule 4 - 共同檔只接受必要憲法

- 寫入目標不是必要憲法時，不得寫入 `constitution/共同/憲法套用規範.md`。
- 寫入目標是必要憲法時，必須寫入 `constitution/共同/憲法套用規範.md`。

## Good Example

- 寫入目標是產出憲法，因此寫入該 Skill 產出的憲法檔。

```text
constitution/api-plan/openapi.yaml.md
```

## Bad Example

- 同一則產出憲法請求改寫共同套用檔。

```text
constitution/共同/憲法套用規範.md
```
