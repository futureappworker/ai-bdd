# Rule 1 - 寫入前讀取該產出的憲法

- 同一次執行中，第一次寫入某份產出之前，必須先讀取 `constitution/共同/憲法套用規範.md`；該檔不存在時，專案套用規則為空，並改以本規範的優先順序執行。
- 同一次執行中，第一次寫入某份產出之前，必須讀取該產出的憲法檔；憲法檔不存在時，該產出的憲法 Rule 為空。
- 產出與憲法檔的對應必須使用下列路徑：
  - `spec.md` 對應 `constitution/specify/spec.md`
  - `checklists/requirements.md` 對應 `constitution/specify/requirements.md`
  - `research.md` 對應 `constitution/technical-research/research.md`
  - `techstack.md` 對應 `constitution/technical-research/techstack.md`
  - `plan.md` 對應 `constitution/system-analysis/plan.md`
  - `contracts/interface.pen` 對應 `constitution/ui-ux-plan/interface.pen.md`
  - `contracts/openapi.yaml` 對應 `constitution/api-plan/openapi.yaml.md`
  - `contracts/schema.dbml` 對應 `constitution/data-plan/schema.dbml.md`
  - `tasks.md` 對應 `constitution/tasks/tasks.md`
  - `implement-run.md` 對應 `constitution/implement/implement-run.md`
- 同一次執行已經讀取過的憲法檔，後續寫入必須沿用已載入內容，不得重複讀取。

## Good Example

- 寫入 OpenAPI 之前先讀取共同套用規範與 OpenAPI 憲法；憲法檔不存在時，憲法 Rule 為空。

```markdown
1. Read 若存在，讀取 constitution/共同/憲法套用規範.md。
2. Read 若存在，讀取 constitution/api-plan/openapi.yaml.md。
3. Write 寫入 contracts/openapi.yaml。
```

## Bad Example

- 沒有讀取 OpenAPI 憲法就寫入 `contracts/openapi.yaml`。

```markdown
1. Write 依 OpenAPI 樣板寫入 contracts/openapi.yaml。
```

# Rule 2 - 點名部位以憲法為準

- 憲法 Rule 點名的部位必須以該 Rule 為準。
- 沒被任何憲法 Rule 點名的部位必須依負責該產出的 Skill 樣板與其既有規範。
- 既有檢查必須把已載入的憲法 Rule 列入通過條件。
- 既有修正必須把未通過的憲法 Rule 改到通過。
- 修正不得把憲法已點名的部位改回 Skill 樣板的預設內容。

## Good Example

- 成功回應 schema 採用憲法的 `code`、`message`、`data`；`operationId` 仍依 OpenAPI 樣板。

```yaml
paths:
  /albums:
    post:
      operationId: createAlbum
components:
  schemas:
    AlbumCreated:
      type: object
      required: [code, message, data]
```

## Bad Example

- 憲法已點名成功回應 schema，修正時仍把該 schema 改回只有資源欄位的樣板預設。

```yaml
components:
  schemas:
    AlbumCreated:
      type: object
      required: [id, name]
```

# Rule 3 - 無法判定時停止寫入

- 同一憲法檔有兩條 Rule 約束同一部位時，必須停止寫入並在回覆回報這兩條 Rule。
- 缺少部位的 Rule 不得套用。
- 要求新增流程階段、改寫 Skill 順序或約束原始碼的 Rule 不得套用。
- 出現上述情況時，必須停止寫入該產出，且不得套用該憲法檔的其餘 Rule。
- `implement` 寫入原始碼或測試時，不得讀取憲法來約束程式內容。

## Good Example

- 兩條 Rule 都約束成功回應 schema，寫入前停止並回報 Rule 2。

```markdown
停止寫入 contracts/openapi.yaml。
回報：Rule 2 與 Rule 1 約束同一個成功回應 schema。
```

## Bad Example

- 兩條 Rule 約束同一部位時，仍套用 Rule 1 並寫入 OpenAPI。

```markdown
套用 Rule 1。
略過 Rule 2。
寫入 contracts/openapi.yaml。
```

# Rule 4 - 不具備該產出樣板時不得直接改檔

- Skill 不具備某份產出的樣板與既有寫入規範時，不得直接修改該產出。
- 需要修改該產出時，必須把缺口交給具備該樣板的 Skill，由它在自己的寫入、檢查與修正中處理。
- `system-analysis` 不得直接修改 `contracts/openapi.yaml`、`contracts/schema.dbml` 或 `contracts/interface.pen`。
- `clarify-over-specs` 可以寫入 `spec.md` 與 `checklists/requirements.md`，且寫入前必須讀取這兩份產出的憲法檔。
- `implement` 可以更新 `tasks.md` 的勾選與 Checkpoint 紀錄，且該次寫入前必須已載入 `constitution/tasks/tasks.md`；檔案不存在時，tasks 憲法 Rule 為空。

## Good Example

- `system-analysis` 發現 OpenAPI 要改，把缺口交給 `api-plan`。

```markdown
Delegate api-plan 修正 contracts/openapi.yaml 的成功回應 schema。
```

## Bad Example

- `system-analysis` 直接改寫 `contracts/openapi.yaml`。

```markdown
Write 將成功回應 schema 寫入 contracts/openapi.yaml。
```
